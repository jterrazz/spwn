# Testing

Three tiers prove Machines, each with one purpose, and a fourth rig runs the menu bar's gate where this Mac has no Xcode. Tier 1 is `make check`: the Go tests (the architecture rules, the contract suites, the few module tests a spec cannot reach), the use-case stories over a fake world, the adapter documents against stub programs, the desktop window's scenarios in Chromium, and the menu bar's stories, every state of its panel drawn against its goldens. Tiers 2 and 3 run the real binary on real VMs of this Mac, outside the gate. Every use case of the product is proved by a story in the owner's words, and a test exists only because a real regression would turn it red.

## The two suites

```sh
make test      # go test ./apps/engine/... ./specs/..., the spec build's world under -race, the window's proof build, then the specs of `specs/` on Vitest: the specs against a fresh build of station and the window's scenarios against its proof build, then the machines and engine/keep use cases again over vz
npm --workspace specs test   # the specs alone, once `make test` built the binary
```

The Go tests come first. The module tests are `*_test.go` files next to the code they judge, kept only for what no session of the binary reaches honestly: a state the terminal driver cannot observe (a busy screen, the renderer's colours), a timing budget, root, a pure algorithm whose edge cases are cheaper at its own level (the renderer goldens: every page fixture of `apps/engine/ui/testdata/pages/`, written by `make generate` from the real page functions, rendered by every renderer of `apps/engine/ui/render/` and compared with its file in `apps/engine/ui/testdata/__expected__/`; `go test ./apps/engine/ui/... -update` rewrites them). The architecture test, `specs/architecture/`, proves each of its rules still bites by judging one violating file in memory; its rules are [Architecture](../concepts/architecture.md#who-may-import-whom)'s. Each contract's suite, `apps/engine/<family>/contract/contracttest/`, runs against its real adapter (over `platform/local/localtest`'s scripted door) and its fake alike, so a fake cannot drift from what it stands for.

The project fake (`apps/engine/project/adapter/fake/`) leaves out what only a disk does, and the project tests of `apps/engine/wire/` (`project_*_test.go`, on the real disk through `local.New`) are the proof of it: a record whose paths were tampered with or hold a control character, a path outside a run folder handed to a write, a record that cannot be written leaving the one before it whole, a link swapped in at the name `project create` makes or under it (with `lay_test.go` beside the adapter), a FIFO that no read waits on, a hard link at a rendered file, a record that does not parse or passes 1 MiB, and a name or path of the declaration that leaves the project, with unreadable files and FIFOs planted beside it. It models no hard link in the declaration, and no test proves that one yet ([TODO](../../TODO.md)).

Then `make test` runs the CLI specs under `specs/cli/` on Vitest, through `@jterrazz/test`. There is exactly one runner, and every spec drives one binary, `.artifacts/go/station-test`, stamped with the version `git describe` prints: the spec build (`-tags world`), which runs the real adapters unless a document hands it a world ([below](#a-use-case-over-a-world)). `make test` builds it once before the runner starts, so no worker links it while another drives a session (with one build per worker, nine links ran beside the first sessions), and tells the runner so (`STATION_SPEC_BUILT=1`): a gate runs that one binary to its end, even when `apps/engine/` changes under it, rather than documents rebuilding it in every worker and half the run testing other code. Run directly, `specs/cli/cli.specification.ts` rebuilds it when it is missing or when any file under `apps/engine/` is newer than it, beside the binary and renamed into its own file, so a worker never executes a half-written file. It is an mtime check, so editing the CLI and re-running the suite always exercises the change instead of a stale build.

`specs/vitest.config.ts` is the one line `@jterrazz/test` derives from `specs/studio.config.ts`, the declaration of the `studio-station-specs` workspace member: its `cli` project collects `cli/`, `adapters/`, and `usecases/` of that folder, and every `*.spec.yaml` there becomes a one-test module driving that runner; its `website` project collects `website/` ([below](#the-windows-scenarios)). A document of `specs/adapters/<tech>/` proves one adapter speaks its program (its argv, its parsing, against the stub CLIs a fixture carries): `.calls` assertions belong there, and nowhere else once a family has moved. The runner's defaults are [the fenced run](#the-fenced-run).

## A scenario is a document

Almost every spec here is a terminal session (a command, its exit code, what it printed), so it is written as one: a `<case>.spec.yaml` in the command's folder, in the literate format of `@jterrazz/test`. The file IS the test; `description:` is its title in the runner, and each entry of `runs:` states the command, its `exit:` and its `stdout:`/`stderr:` byte-exact.

```yaml
# specs/cli/root/unknown-command.spec.yaml
description: an unknown command is one error block on stderr, without colour, and exits 2
runs:
    - command: nope
      exit: 2
      stderr: |
          Error: unknown command "nope" for "station"
          Hint: run station --help
```

A document may stand on ground of its own: `fixture: ./__fixtures__/<case>/` spreads that folder into the working directory, which is the run's `HOME`, so a stub program under its `bin/` answers the binary. Ground sits in a special folder spelt with double underscores; a subject folder never starts with one. Where a stream is long and only some of it is the claim, the command writes it to a file (`help > help.txt`) and `files:` asserts what it `contains`.

`TEST_UPDATE=1 npm --workspace specs test` rewrites the `exit:` and the streams of every document from what the binary actually printed: deliberately, after a change to a command's output, and never as a way to make a red suite go green. Nothing else in the file is touched.

## The fenced run

No spec reaches the real machine. A run's environment is the runner's defaults, what its document states, and of the runner's own variables only the temp root `@jterrazz/test` points `TMPDIR`, `TMP` and `TEMP` at: every other variable of the runner is unset, so a cache folder a gate exports (`GOMODCACHE`, `GOCACHE`, `npm_config_cache`) is never the folder a fixture's stub empties, and GitHub's Ubuntu runners' `XDG_CONFIG_HOME` never makes every run share one folder of preferences (`specs/cli/root/runs-inherit-no-runner-variable.spec.yaml` lists what a run holds). The runner sets `HOME` to the run's working directory; the `terminal` env names the terminal `xterm-256color` with `COLORTERM=truecolor`. It sets `PATH` to its `bin/` alone (the fixture's stubs), and `STATION_SYSTEM_DIRS` to nothing, so a system program no fixture stubs is "not found" alike on a Mac and on the Linux CI runner (the manager folders the binary adds to its own search, `/opt/homebrew/bin` and `/usr/local/bin`, are read under that root too, so a fixture's installer lands a manager in `root/opt/homebrew/bin` and never meets the owner's), and `STATION_SYSTEM_ROOT` to the run's `root/`, so `/Applications`, `/opt/homebrew` and `/Library` are read there and the owner's own apps are neither listed nor sized; the disk is the staged volume's, a Mac's 1 TiB with half of it free, whatever disk the machine running the spec has, so no finding or number of a spec depends on its free space. `STATION_POWER_STUB` points the IOKit contract at the run's stub folder (a fixture writes one): its files are the reading, every assertion and clamshell call is a line of `.calls`, and with no such folder the run has no IOKit contract at all, so no spec takes a real assertion. `STATION_KERNEL_STUB` points a Mac's counters and process tables at the run's `kernel/` folder, recorded kernel tables (`counters.json`, and `procs.json`, the process tables successive reads walk through), and with no such folder the kernel answers nothing, so no spec reads the real machine's activity. It also pins `NO_COLOR=1`, `COLUMNS=80`, `TZ=UTC` and `STATION_MACHINE_KIND=mac`, so every stream is the pipe form and a document means the same thing on every machine: the pinned kind also picks the adapter the machine reads itself with, so a Linux runner reads a pinned Mac as a Mac. A fixture's script holds to the same rule: it calls what a Mac and an Ubuntu runner answer alike (`perl` for a date, a crop by character or a unix socket, `ls -l` for a mode), never a BSD-only or GNU-only flag.

## A diff of HOME

A spec that installs or sets up states the whole change a run made to `HOME` as its `stdout:`, so a file written that nobody expected turns the spec red; `files:` judges one listed path at a time and cannot say that.

`specs/cli/install/__fixtures__/home-diff/` is the ground that holds `home-diff`, spread into the run like any fixture. `home-diff mark` copies `HOME` into the run's own `TMPDIR`, and `home-diff` alone prints what `HOME` became since the mark. The stubs (`bin/`), `.calls` and the mark itself are left out of both sides: a stub is not the machine, and `.calls` is asserted with `files:`.

```yaml
# specs/cli/install/fresh-init.spec.yaml (shortened)
runs:
    - command: '--version >/dev/null; home-diff mark; "$STATION" init --name m </dev/null >/dev/null; home-diff'
      stdout: |
          ~/.config/station/
            + preferences.json 0600
              ...
```

The output is one block per folder, folders and names sorted bytewise, and a folder no block names is unchanged: that is the exactness. Each line states one change under its folder.

| Line                 | Means                                                                                                                             |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `+ name`             | A file added; a text file under 4 KiB shows its content, indented, anything else one `<n> bytes sha256 <hex>` line                |
| `- name`             | A file removed                                                                                                                    |
| `~ name`             | A file changed; a text file under 4 KiB shows a unified diff from its first `@@`, anything else `before -> after` size and sha256 |
| `+ name/`, `- name/` | An empty folder added or removed; a folder with files is never listed, its files say it                                           |
| `+ name -> target`   | A symlink added, `~` when its target changed                                                                                      |
| `keychain` block     | The entries of the `security` stub, by `service/account` alone                                                                    |

A mode follows the name only when it is not `0644` or when it changed, so a file the binary writes private reads `0600` and an ordinary one carries no noise. No time, owner or inode is ever printed, and a secret is never printed: the `security` stub of `specs/adapters/__fixtures__/setup-stubs/` keeps an entry as an empty file `.keychain/<service>/<account>`, its value reaching `.calls` through the stdin it was sent on and nowhere else.

`TEST_UPDATE=1` rewrites the diff like any stream, and the review of that rewrite is the review of what the run changed. `home-diff` computes its unified diffs itself, in the form `diff -u` prints with three lines of context, so no platform's `diff` can change a golden; a mode reads with the group and other write bits cleared, so a runner's umask changes none either.

## A use case over a world

A document of `specs/usecases/<family>/<verb>/<outcome>.spec.yaml` tells one outcome of one call (`machines/stop` is `machines.stop`; `engine/<job>` is an engine job; `root/`, `remote/`, `output/`, `errors/`, `migrate/` and `security/` hold what spans calls) against a seeded fake world, and asserts what the owner reads, never an argv. It names its world as an env set, `env: two-macs`: the runner registers one per file of `specs/usecases/worlds/`, which points `$STATION_WORLD` at `world.json` in the run's directory and seeds it from that file at the first run. Every run then reads and writes that one world, so a document can say what the world became by reading it back through the CLI.

A story reads as the owner's session: commands, what they printed, then a world event and what the owner reads after it.

```yaml
# specs/usecases/machines/stop/server-confirmed-stays-stopped.spec.yaml (shortened)
description: "a server stopped with its name typed wants to stay stopped: its Mac's reboot does not start it"
env: [two-macs, terminal]
runs:
    - command: '... machines stop infra --on mac-mini --confirm=infra'
      stdout: |
          On mac-mini:
          ✓ infra · stopped · wanted state: Stopped
    - command: 'world reboot mac-mini'
    - command: 'machines --on mac-mini'
      stdout: |
          ○	infra	Server	mac-mini	Stopped · always on	8 CPU	24 GB
```

The worlds are the files of `specs/usecases/worlds/` (`two-macs`, `one-mac`, `mini-offline`, `in-workspace`, `in-server`, `on-battery`, `serve-off`...), each the ground of many stories. Each Mac of a world seeded with an engine keeps a release reading answered at the world's `now` (`stores.release`), so its engine's release job asks the world's GitHub nothing at its start, and each server such a Mac runs in the seed keeps an uptime record started at that `now` (`stores.uptime`), so the moment its engine first sees it healthy, a tick earlier or later under load, never stamps it; `release-unasked` is the one world whose Mac never asked, with `v0.22.0` out, the ground of `engine/release/at-start`; `release-never-asked` keeps nothing, its engine stopped before its first ask, and `release-first-refused` has its first ask refused by a scripted fault. A world event is the hidden `station world <event> [args]` of the spec build, from the closed list of `apps/engine/world/events.go`: a Mac's `reboot`, `power-cut`, `unlock`, `offline` and `online`, `engine-crash`; `knock <mac> <from-mac> [not-the-engine]`, the second Mac's device key at the first Mac's door, judged by what the first Mac's running engine holds, or with `not-the-engine` by a process of that Mac that never took the book's start read, which prints the door's line and changes nothing; a VM's `crash`, `poweroff-inside`, `reboot-inside`, `console` (a line its console writes), `address`; `listen` and `unlisten` a port, `container-run`; `edit` a file by hand; `project <root> [error|warning|info|drift <path> <message> [hint: <hint>]]`, a project of This Mac at that absolute folder, and an issue its plan finds or a row of its drift, with the hint after the word `hint:`; `project <root> render <agent> <path> [<content>]`, what that agent's harness renders at a path of its run folder (no content: it renders nothing there any more); `project <root> edit <path> [<content>]`, the owner writing a file of a run folder by hand, a path from the root (no content: deleting it); `project <root> link <path> <target>`, a link at that path from the root, in the declaration, on a run folder's way or the record, which a project refuses to follow; `project <root> fifo <path>`, a FIFO at that path, which a project refuses to read; `readonly <folder> [off]`, a folder of the project without its write bit, in which apply makes, replaces and removes nothing; `building` an image's build at a step, running on This Mac; `unplug`, `plug`, `close-lid`, `open-lid`, `will-sleep`, `thermal`, `battery`, `low-power`; `advance` the clock; `fault` and `hold` a contract's method, `unhold` to let go; `upgrade` a Mac's or a VM's station; `slow`; `reads` a fact; `unopened`, an app never opened on a Mac, so a command it brings at its first launch is absent; `certificate`; `local-network <mac> approved|not-approved`, how that Mac stands with macOS's Local Network approval of station: while not approved, the fake dial to any of its VMs is refused as macOS refuses it, and that Mac's engine reads it at its start; `agent <mac> held <pid> [<executable>] [<label>]` and `agent <mac> served`, another process holding that Mac's ssh agent socket, which its engine reads at its start, then letting it go; and an agent's hook firing inside a VM, `agent-prompt`, `agent-step` (a step, its output a PR's URL opening the PR), `agent-notify`, `agent-stop` and `agent-end`, each folded into that VM's journal. Any other event changes only the world; what Machines does about it is what the next command shows.
The world (`apps/engine/world`) holds what is outside Machines, one slice per family: the repositories a shared source is read from, at each commit; each Mac's engine (its job, when it started and when the owner stopped it, and the activity it kept before the world's now, as profiles of `activity.Profile` the world unfolds once when it is read, its newest point the sample the meter answers then), the station it runs (an older version, and the calls it `lacks` until `world upgrade`), preferences, the files a store has not read yet (a hand edit, a file station v2 left), the owner's package files and Machinefiles (`world edit <mac> machinefiles/<name>.yaml`) and Machines' other stores, its Self, its battery and lid reading, what listens on it, its tailnet node, its installers, meter (its counters, how much each grows a second on the world's clock, and optionally a `load`: a seeded curve of the busy share, one level a slot of `slot_seconds` between `floor` and `ceil` thousandths, drawn from the seed and the slot alone, so two reads apart differ and two runs of one world agree byte for byte; the play world gives each running VM one, seeded by its name), disk, jobs, vault, its sign-ins, passwords and grants (`accounts`, with the logins its fake is scripted to answer), facts and ssh config, its images and VMs (what Machines keeps of a VM, beside its disk, its run and when it began and ended on the world's clock, its guest and what listens in it), and the faults scripted for the fakes. Under `$STATION_WORLD` the spec build wires every family's `adapter/fake` over its Mac's slice instead of the real adapters (`apps/engine/wire/world_on.go`, the one file that knows the tag; `release_test.go` fails when a family's fake is not linked), runs each Mac's engine inside the command, stepped over the world's clock until it is quiet, each step once its VMs' guests have greeted it, and an engine another engine begins handed to that engine only once they have, so what it reads of their guests never depends on the gate's load (the clock moves only for the command that waits, a tick and an advance: what the engine runs in its own lifetime waits for it, and so does a watch that follows a VM's create, as the window holds one open; a reading it runs beside its loop, such as a VM's drift, runs once the command is done and takes none of its time, so the next command reads it), and reaches another Mac of the world in-process, through the wire form. A VM of the world answers each guest exchange from no reading shared with the one before, as each is a process there. A world event is a run of the hidden `world` command, `command: 'world reboot mac-mini'`; its closed list is `events()` in `apps/engine/world/events.go`; an event no fake models yet is refused as such. `world edit <machine> <file>` gives a file of Machines the text on its stdin, as a hand edit would. `world fault Hypervisor.Boot [2 times]` fails that contract's method the next calls (every call, without a count) in the fakes that obey it: `Hypervisor.Boot`, `Installer.<verb>`, `Bundler.Bundle`, `Jobs.Install`, `Jobs.Start`, `Listeners.Read` (what listens on a Mac cannot be read, so its ports read fails), `Tailnet.Share`, `Unlocker.PlannedRestart`, `CheckRunner.Run`, a server's check that stops answering, `Meter.Sample`, a Meter that does not answer, `Hypervisor.Disks`, a hypervisor that cannot list its disks, and `EndpointDialer.Dial`, a Mac whose ssh answers with no station there. A fake installer answers each contract method as its real adapter does (`apps/engine/wire/fake_installers_test.go` holds every method of the registry to it): it names the same manager and abilities, and a method that keeps no list (`script`, `shell`, `provided-by`, `app`) answers `ErrUnlisted`, so what such an install leaves is read by the app's own check, which the world answers from what was installed (`apps/engine/apps/adapter/fake/footprint.go`). `world hold <Contract>.<Method>` makes the next call of that method wait until it is interrupted (`Installer.<verb>` and `Bundler.Bundle` after their first package, `Hypervisor.Clone`, `Hypervisor.Boot`; `Unlocker.PlannedRestart` is a restart that never comes back). A held hypervisor call first writes its run's world back and lets go of it, so the `run` step of a terminal document reads, with a command of its own, what the held create has made so far (`machines/list/creating-while-cloning`). A hold the world file declares in its `script` for one VM of one Mac (`{"call": "Hypervisor.Boot", "hold": true, "mac": "mac-mini", "vm": "linux-2"}`, two-macs') is never spent: that VM's call waits for the world's life, so its create stays at that step and every read meanwhile sees it there (`machines/list/creating-held-by-the-world`); while that call waits, the world file lists the hold under `held`, gone once the call goes on, so a reader of the file (the window's recorder) asks its reads once the hold is reached; a run that ends with the call still waiting leaves it listed, as it leaves the hold. `world unhold <mac> <vm>` lets go of the holds declared for that VM, and `world unhold` alone of every hold the script keeps, a hold of the next call not yet taken included: the held call reads its world's file until its hold is gone from it, then goes on as if never held, so the create ends (`creating-held-by-the-world-let-go`). An unhold with nothing held answers with no error (`unhold-with-nothing-held`), so a recorder runs it after every gesture.

A VM a create made gets a slice of its own the first time its guest is asked (`madeSlice`, `apps/engine/wire/world_on.go`), so a call at it runs the real call in that slice and a story reads what it changed there (`.macs["web"]`). The slice is a Linux machine sized as the VM, its user's sudo asking no password as station's image makes it. One made from a Machinefile holds the Machinefiles of its Mac as they were at the last `images build` of that Machinefile (the fake store keeps them with the image's record, `world.Mac.Built`), or as they are at the create when the world built none, and carries out once the image phase of that Machinefile before anything else asks its guest: that is what its image baked, so a package added to the bake list since the build is not there (`boot-phase-old-image-shows-drift`), and no fault or hold a story scripted reaches it (`world.Baked`). Deleting a VM deletes its slice with its disk, so a VM made again under its name starts from its image. A script the guest is given whose lines copy a file under `~/.config/station/` leaves that file in the slice, as a shell would. Its guest runs as another process does: the steps the Mac's act records never reach it, only the act's end does, and the world's clock, one for every process, which a guest of a waiting run waits on as that run does (`from-machinefile-installs-what-its-image-lacks`, `from-machinefile-kept-with-its-phases`).

The window reads a world through `station guest serve --stdio` of the spec build, its door onto the engine's socket (`apps/desktop/scripts/world.py`), so in a world run on a Mac that door answers as the socket does: a frame whose `target` is another Mac, or a VM of another Mac, rides the run's Router to that machine of the world, and one of a Mac that does not answer is refused as the socket refuses it (`remote.unreachable`, `remote.vm-mac-unreachable`), never answered by This Mac (`specs/usecases/overview/read/far-server-*`). While the world says This Mac's engine does not run (stopped, never set up, or its Mac locked), such a frame is refused as an absent socket refuses it, "the engine is not running" (`far-mac-engine-stopped`). A frame for This Mac or one of its VMs keeps the stdio door's own rule, and outside a world nothing hops to a third machine (`apps/engine/wire/remote.go`, `socketDoor`).

Every story is also a leak check. The spec build arms the tripwire of `apps/engine/core/secret` when it starts: a frame the engine serves, an answer the world's second Mac sends back, a write of the CLI or a sealed page that carries a secret of the world (its Macs' `vault` and `secrets`) or a token shaped by its issuer panics, and the story goes red on the words `tripwire: an answer carries a secret`, the secret itself withheld. The release build never arms it.

A second hypervisor must pass the VM use cases unchanged (AR-02), so `make test` runs `specs/usecases/machines/` and `specs/usecases/engine/keep/` a second time with `STATION_SPEC_HYPERVISOR=vz`: the runner then sets `$STATION_WORLD_HYPERVISOR` in every world, and each Mac that had Machines' own hypervisor runs the fake `vz` instead (a Mac whose world says `"hypervisor": "none"` keeps none). The env sets `two-macs-tart` and `two-macs-vz` are two-macs over that hypervisor in both passes, for a document whose sentence names it (`machines/list/a-hypervisor-that-does-not-answer-is-said` over tart, `...-under-vz` over vz).

`specs/architecture/coverage_test.go` reads the registry and walks `specs/usecases/`: every call needs a story of each outcome it declares (done, each code it may end in, `not-for-this-machine-<machine>` for each reference machine its rule refuses, `on-another-machine` when it is routable), and a document names only a real call and outcome. The calls not covered yet are its allowlist, which only shrinks. `release_test.go` proves the release binary links no world and no fake.

## A document that needs a terminal

A run is never given a terminal, so a document that needs one names the `terminal` env set and runs `--version >/dev/null; terminal "$STATION" [words]`. The `terminal` stub of `specs/__fixtures__/terminal/`, which any noun's document lists in its `fixture:`, opens a pseudo-terminal (80x24, or `--size`), replays what the binary draws on a screen of cells, and plays the steps the document writes on `stdin:`: `see` and `gone` wait for a text on the screen (10 s; `within SECONDS see TEXT` bounds the wait, so a document can say a row appeared before a slow read ended), `file PATH` waits for a stub to have written PATH, so a step can follow a read's start, `run COMMAND` runs a shell command beside the binary and fails unless it exits 0 (a world event while a screen is shown, or a look at what a key changed), `send` types keys (`\r`, `\x1b[B`), `settle` waits until the binary has drawn nothing for 0.2 s (1 s at most), so the next key reaches the frame the last one drew, `clipboard TEXT` waits for the binary to set the clipboard to TEXT (OSC 52), which also lands in `./clipboard` for a `run` step to read, `screen` prints the screen, and `scrollback` waits for the binary to exit and prints the history above the screen with the screen, as tmux keeps it (a clear from the screen's first cell joins the history), so a document can count the copies a live read leaves; `asked` waits for it to exit too and prints how many times it asked the terminal for its background colour, which the screen answers as a dark terminal does. It then exits with the binary's code, and a wait that times out, or a `see`/`gone` the binary exits before, prints the screen, the bytes the binary drew and the seconds it ran on stderr and exits 124, so a binary that never started reads apart from a slow first frame; one the driver could not run at all (exit 127) prints why on that screen, the call that failed and its errno. The screen is a terminal with synchronized output: a step reads the last frame drawn whole, never one half drawn. The size is set before the binary starts, so its first frame never races the driver for it. A live read (`overview`, `apps`, `disk`, `machines`), `init`, the settings that ask values, the confirm gate of a destructive verb and `machines unlock` drive the binary this way.

The full grammar is `@jterrazz/test`'s [Spec documents](https://github.com/jterrazz/package-test/blob/main/docs/guides/spec-documents.md) and [CLI specs](https://github.com/jterrazz/package-test/blob/main/docs/guides/cli-specs.md).

## The stubs

A spec copies one `fixture:` directory into its working directory, so stubs live beside the command word that uses them: `specs/cli/<noun>/__fixtures__/<case>/bin/<tool>`. A fixture both suites read (the VMs `vms/`, the running VM `engine-vm/`, what Tailscale serves `serving/`, the Machinefiles of the VMs `api` and `linux-1` that install Vite and Expo `dev-servers/`, the two Tailscale apps) lives in `specs/__fixtures__/`, the lowest folder `specs/cli/` and `specs/adapters/` share. A stub answers by argv from a table, appends `<tool> <argv>` (and the stdin of `brew bundle --file=-`) to `$HOME/.calls`, and exits 97 on anything unscripted. A document asserts `.calls` through `files:` to prove which installer line ran. The GitHub API is a stub backend the runner serves, reached through `STATION_GITHUB_API_URL`; a VM's sshd is the stub `vm-sshd` (`specs/cli/__fixtures__/vm-sshd/`), served to the documents that declare `serve: sshd` and reached through `STATION_GUEST_SSH_PORT`.

## What a test is for

A test exists because a real regression would turn it red. Every behaviour of a command (each flag, refusal, exit code, `--json` schema and migration) has a spec document through the real binary; the architecture test proves the layers; a module test exists only where the logic is dense and a spec cannot reach it honestly (what the terminal driver cannot observe, a timing budget, root, a pure algorithm). A test that restates a declaration, a table or a mock's own return is deleted.

### The wash and the zoom

`STATION_CAPTURE_SET=native,opening,walls` measures the two things the panel must not do, on the real panel. `native` opens the Apple menu twice over each wall in each scheme, with the same desk laid under it as under the panel, since the Tahoe capture found it on the panel's own material. `capture/tint.py` takes the median CIELAB of each surface's glyph-free pixels over the rectangle both cover, and the wash passes when the panel is within 4 CIEDE2000 and 3.5 on b\* of the menu, on every desk. The bars hold the system: Passwords' panel against the Apple menu, measured as one material, sits at 2.7 and 2.8 (b\* 0.7, 0.3), and two openings of the menu agree to 0. They are set on the owner's pick of [ADR-053](../decisions/053-the-panel-is-untinted-glass-over-a-grey-ground.md), one step above its worst desk (3.69 and 3.28, dark over the colour wall), where the tinted glass it replaced fails light over the dark wall (7.26, -4.55); `baseline.json`'s `round6` holds both runs.

`STATION_CAPTURE_SET=dock` judges Spwn's icon where a person sees it. The run builds `Spwn.app` (`make window`), which carries the menu bar inside it with no Dock tile of its own, and the driver installs it in the guest's `/Applications` alone, pins it in the Dock between Safari, Notes, System Settings and Terminal at 64 pt over a plain mid-grey desktop (`capture/wall.swift grey`, saturation 0, so every translucent tile sits on the same ground), then takes the six icon appearances in turn: the scheme and `AppleIconAppearanceTheme` (`RegularLight`, `RegularDark`, `ClearLight`, `ClearDark`, `TintedLight`, `TintedDark`) are written, the Dock restarts, and each tile is cropped at the frame the Dock's accessibility elements give. `capture/dock.py` reads each tile's mean luminance and saturation over its middle 60 %, and passes when Spwn's falls inside the range of the Apple tiles of the same capture in each of the four mono appearances, where a flat bitmap stays a bright tile among grey glass. It writes the judged tile's difference against its nearest Apple tile, `dock-verdict.json`, and `board.png`, a row per appearance; the two regular appearances are on the board for the eye, and `measure_test.py` holds the verdict to synthetic tiles.

The footprint test: the home is listed (depth 4) before the first step and after every step, and every new path must be one a Disk row holds (`station disk --json`) or [Footprint](../reference/footprint.md) declares, a home-root exception of Footprint, a path the OS writes itself (`specs/machine/<kind>/os-noise.txt`, never an app's), or one the suite's own native commands put where their user asked (`specs/machine/suite-made.txt`: `uv tool install` links into `~/.local/bin`). An unmatched path fails the suite, named with the step that made it. `station disk free` must leave every Can rebuild row empty and every Your data row untouched, and `station disk erase go --confirm=go`, on a fresh clone of the macOS VM, must take only go's data.

## The gate scripts

The scripts that prove a change on the shared Linux VM live in `scripts/gates/` at the repository root, so a session reads one folder and every machine runs the same code. [ADR-066](../decisions/066-a-commit-owes-that-it-builds-and-lints-a-lot-owes-the-gate.md) sets the two tiers and [ADR-067](../decisions/067-one-train-appended-by-makers-proved-at-its-tip.md) the train; these are the commands that run them.

| Script                                                  | Runs                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc.sh <worktree> <base> <label>`                       | The per-commit loop over `base..HEAD`: `CHEAP=1` (or `true`, `yes`) is the cheap tier (gofmt, vet, golangci, `make lint`, the repository root's `make lint`, the world build); `0`, `false`, `no` or nothing is the heavy tier, and any other value is refused. It prints one `VERDICT` line per commit |
| `cold-gate.sh <worktree> <branch> <label>`              | One cold `make check` of a tip in a fresh clone, then the repository root's `make lint`, holding the VM exclusive; given the repository root it enters `machines/` itself                                                                                                                               |
| `desktop-proof.sh`, `regen.sh`, `fold.sh`, `ratchet.sh` | The desktop proofs of a tip, the forced regeneration of the generated worlds and its fold into a rebase, and the pixel-golden byte count per commit                                                                                                                                                     |
| `tip-mac.sh`, `darwin-build.sh`                         | The Mac proofs of a tip: the menu bar check, then the darwin build in a tart VM, each through the gate slot                                                                                                                                                                                             |
| `gate-slot.sh <command>`                                | The one workstation-wide slot a full gate takes, by priority                                                                                                                                                                                                                                            |

A run writes its logs, end files and locks under `GATE_RUN_DIR` (default `.artifacts/gates/`), reaches the VM named by `GATE_VM_LINUX` (default `development-linux`) and keeps its files in `~/$GATE_VM_DIR` there (default `spwn-gates`); the VM's homes, its heavy-run lock and its ports are the estate's development-VM page. Each launcher starts its work on the VM under `setsid` and waits on an end file, so a killed shell never kills a run.

The VM's own story slot (`take_slot` in `cc-remote.sh`, two holders) follows the same load rule as `gate-slot.sh`: a free slot is taken only while the VM's 1-min load is under `STORY_SLOT_MAX_LOAD` (default twice `nproc`); after `STORY_SLOT_LOAD_WAIT` seconds (default 900) of a loaded VM it proceeds and logs the load. The stories then run on `STORIES_WORKERS` workers, by default the cores the load leaves free (2 to 8), and no story timeout is raised for a loaded VM.

Every clone a script makes on the VM lands in `GATE_VM_RAM` (default `/gates/<GATE_VM_DIR>`), on the VM's RAM disk, so a throwaway tree never reaches the disk the Mac's SSD backs; logs, bundles and end files stay in `~/$GATE_VM_DIR`. The cold gate clones to one fixed path, `cold`, since the exclusive lock lets one run at a time, and a cheap commit to its cheap slot's `cc-wt-s<n>`, whatever its label: Go's build cache is keyed by the directory, so it hits from one run to the next. A loop deletes its label's node clone when it ends. When that RAM disk is at or above the 90 % guard (the clones of other lots fill it), the `cc.sh` loop says so in the first lines of its log and clones under `~/$GATE_VM_DIR/clones` on the VM's disk instead, slower and not refused; it refuses only when the VM's own disk is at or above the guard.

A launcher creates `~/$GATE_VM_DIR` on the VM itself, so a new `GATE_VM_DIR` needs no setup.

The slot serves `GATE_SLOT_PRIORITY=landing` first (a gate that lands work on the train), then `normal`, then `low` (a bench, a capture, a rig run); a waiter never takes the slot while a waiter of a higher priority waits. The scripts close the lock descriptors (3 to 9) before they start a child, so a fixture server left behind by a story never holds the heavy-run lock. `scripts/gates/test.sh`, run by the root `make lint`, parses every script and proves the priority order.

### Usage and knobs

The scripts carry no usage header: a comment states an invariant, a hazard, an outside fact or a value, so what a script takes is here, and a script that is called wrong prints its one `usage:` line.

- `cc.sh`: `BRANCH=<name>` loops that branch instead of HEAD's; `PICK="<n> <n>"` runs only those 1-based positions and `FROM=<n>` skips the commits before the n-th; `ONLY=<step[,step]>` runs those steps alone (`STATIC GEN GOTEST MAKELINT ROOTLINT STORIES`; `DRIFT` is `GEN`, `1` is `STORIES`); `UPD=1` re-records the stories; `PAR=<n>` commits at once (4 under `CHEAP`, else 1); the default filters are `cli usecases adapters`. A `FLAKE` reruns its failing step alone once. The loop runs on the VM under `setsid`, writes `<label>-cc.end` when it ends (or `<label>-cc.detached` if the launching shell dies first; `ATTACH=1` waits on it again), and exits as [Exit contracts](#exit-contracts) says. Each commit ends in a `VERDICT` line (`tier=cheap` or `tier=heavy` is the tier that ran), `cc-verdict.py` judging the five known flakes by signature. The launch line states the tier too; the raw `CHEAP` word is never printed.
- `cold-gate.sh`: `GATE_SLOT_PRIORITY=landing|normal|low` and `GATE_VITEST_WORKERS` (default 12); the log is `station-<label>-cold.log`. The script takes the gate slot itself, so it is never wrapped in `gate-slot.sh`.
- `gate-slot.sh`: waits while the 1-min load where it runs is at or above `GATE_SLOT_MAX_LOAD` (20); `GATE_SLOT_VM=<ssh name>` counts that VM's load too, the higher of the two. A waiter prints who holds the slot every 10 minutes (the holder's `pid`, `since` and `cmd` are under `gate-slots/1/`).
- `darwin-build.sh <worktree> <label>`: run as `GATE_SLOT_PRIORITY=low gate-slot.sh bash darwin-build.sh`; `DARWIN_STEPS` adds commands run in the VM's repository after the build and vet, `DARWIN_OUT` copies the binary to a path on the Mac, `DARWIN_VERSION` stamps the version. It bundles HEAD, installs the pinned Go (sha256 checked), runs the release build and `go vet` on darwin, then `cargo test --bin spwn-window` in `apps/desktop/src-tauri` (no other gate runs the window's Rust tests) and `scripts/sign-macos-test.sh`, the signing script's checks over a fixture bundle, prints `PASS darwin-build <sha>` or `FAIL` and deletes the clone.
- `desktop-proof.sh <worktree> <label> [branch]`: runs `desktop-proof-remote.sh` detached on the VM and waits on `<label>-dt.end`; its output is `<label>-dt.out`. Every stage runs whatever an earlier one returned, except that the stages after the clone and `npm ci` cannot run without them; it ends in `VERDICT <label> <sha> GREEN|RED steps=<red stages>` (`steps=-` when green), where a stage that returned non-zero or never printed counts as red.
- `regen.sh one <worktree> <sha> <label> [aria filter]` and `regen.sh all <worktree> <map file> <prefix> "<lane A>" "<lane B>"`: the forced regeneration of `machines/` twice (determinism), the changed files back under `<label>-regen-out/`, the list in `changes.txt`; `fold.sh <old sha> <label>` (a rebase exec line, `GEN_DIRS` overrides the folders) amends that output into the old sha's commit; `ratchet.sh <worktree> <base>` prints `<sha7> bl=<baseline> png=<sum> EQ|DIFF` per commit.
- `tip-mac.sh <worktree> <tip sha, 9 chars> <label>`: the menu bar check plain, twice with `--update-goldens`, then the darwin build, each through the gate slot; it refuses when HEAD is not the tip.
- `env.sh`: sourced by every launcher, never run; `GATE_RUN_DIR`, `GATE_VM_LINUX`, `GATE_VM_DIR` and `GATE_VM_RAM` are read nowhere else. The launchers hand the RAM folder to the scripts they run on the VM as `CC_WORK`, and their files folder as `CC_HOME`.

### Exit contracts

A launcher's exit code and the last line it prints agree, so a reader and a wrapper reach the same verdict: a gate is read from its exit code, and a `VERDICT` line says which steps. `2` is a usage error everywhere, `90` a bundle that could not be made and `91` a copy to the VM that failed.

| Script                         | Exit 0                                                                               | Non-zero                                                                                                                                                                                                       |
| ------------------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cc.sh`                        | every commit GREEN, or a FLAKE whose rerun was green, one `VERDICT` each             | 1 a commit is RED; 2 also a `CHEAP` value refused; 86 disk; 87 VM not free; 88 loop already running; 93 no verdict yet, the loop still runs (`ATTACH=1`); 94 the loop ended without a verdict for every commit |
| `cc-loop.sh` (on the VM)       | every commit has its `VERDICT` and the `SUMMARY` printed: the verdicts are the log's | 86 disk; 88 a loop of the label already runs                                                                                                                                                                   |
| `cc-remote.sh` (on the VM)     | the commit ran to `CC-DONE`; `cc-verdict.py` judges its stage lines                  | 83 to 85 a slot or the heavy-run lock not taken; 9 the clone                                                                                                                                                   |
| `desktop-proof.sh`             | every stage line is `0` and `DT-DONE` printed                                        | 1 a stage is red, or no end after 3 h (then no `VERDICT` line)                                                                                                                                                 |
| `cold-gate.sh`                 | generate, `make check` and the root `make lint` all returned 0                       | the remote's code: 1 a red step, 84 slot, 95 to 99 setup                                                                                                                                                       |
| `tip-mac.sh`                   | the menu bar check (plain and both updates) and the darwin build passed              | 1 a red step, named in the closing `VERDICT` line                                                                                                                                                              |
| `regen.sh one`                 | both runs, the render and the determinism check passed, the output fetched           | the remote's code, or 1 when the output could not be fetched                                                                                                                                                   |
| `regen.sh all`                 | every commit of both lanes regenerated                                               | 1 a lane had a red commit                                                                                                                                                                                      |
| `darwin-build.sh`              | `PASS darwin-build`                                                                  | 1 `FAIL darwin-build` with the step                                                                                                                                                                            |
| `gate-slot.sh`, `hold-then.sh` | the wrapped command's own code                                                       | the wrapped command's own code; 2 an unknown priority                                                                                                                                                          |
| `fold.sh`                      | the old commit's generated folders now match the regeneration                        | 1 any step or count that does not match                                                                                                                                                                        |
| `ratchet.sh`                   | always: it prints `EQ` or `DIFF` per commit and the reader judges                    | none                                                                                                                                                                                                           |

## What CI runs

`.github/workflows/check.yaml` calls the shared `studio-actions` check workflow on every push and every pull request to `main`; what that workflow runs against a repository's `make` targets is [The stack](../concepts/stack.md)'s. Locally the same gate is `make build` then `make check`. CI's Lint job runs the repository root's `make lint` (Go lint, the TypeScript toolchain's comment and architecture rules, the gate scripts' test), which `machines/`'s own `make lint` does not, so the cheap and heavy tiers and the cold gate run both: a red CI Lint is caught before a push.

The npm half is linted by the same toolchain as every other repository: `npm run lint` is `typescript check`, and `make lint` runs it after the Go half ([Develop](develop.md)).
