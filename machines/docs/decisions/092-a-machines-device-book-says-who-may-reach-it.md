# ADR-092: A machine's device book says who may reach it

**Status:** Proposed
**Date:** 2026-11-25

An agent leaves the status `Proposed`; only the owner writes `Accepted`.

Amends [ADR-077](077-a-workspace-trusts-its-macs-device-key-first.md), [ADR-064](064-a-key-never-leaves-its-device.md) and [ADR-090](090-a-machine-is-reached-through-its-engines-door-never-through-openssh.md).

Decided by the orchestrator on 2026-11-25, under the owner's delegation of that day, on the open points of the device book's plan: the verbs, the code noun, presence on add, and what the book deletes.

## Context

A VM trusts three things today: its Mac's device key, the Mac's `~/.ssh/id_ed25519.pub`, and every line of the Mac's `~/.ssh/authorized_keys` ([ADR-077](077-a-workspace-trusts-its-macs-device-key-first.md)). So whoever may log into a Mac may reach its VMs, and a key added to that file for any reason opens them all. ADR-077 and [ADR-064](064-a-key-never-leaves-its-device.md) §4 both say the copy and the personal key leave "with the device book", which no record defines. [ADR-090](090-a-machine-is-reached-through-its-engines-door-never-through-openssh.md) builds its door on that book, names its gesture `spwn devices allow`, and lists a `hello` channel.

Three facts bound the design:

- The engine's API marks no frame as come from another machine: a frame relayed by `engine attach` reads like one from the local socket.
- The key agent signs any data it is given, so any process that reaches `agent.sock` can make this Mac's device key sign a file's content.
- [ADR-021](../../../docs/decisions/021-one-program-spwn-one-command-for-everything.md)'s verb table is closed: adding to a set is `add`, and `allow` and `list` exist nowhere.

## Decision

1. **Each machine keeps a device book**: the list of the OTHER devices allowed to reach it. It is `~/.local/state/station/devices.json`, mode 0600, beside `vault.json`. It holds its generation and its entries; each entry holds a name, a public key, the channels it may open, when it was added, and a seal. This Mac's own device key is never an entry: its own VMs always trust it. In code the noun is `devices`, never "book", which is the vault's.
2. **An entry passes five rules**, each refused by its own code:
    - its name passes the machine-name rule;
    - its key is `ecdsa-sha2-nistp256` (a device key) or `ssh-ed25519`, and nothing else;
    - no name and no key appears twice;
    - its key is not this Mac's own device key;
    - its channels are a non-empty subset of `spwn-api`, `pipe` and `herdr`, all three by default.
3. **The commands follow ADR-021's table.** `spwn devices` reads the book (`--json`), and works with the engine down and `--on` another machine. `spwn devices add <name> <public key> [--channels …]` adds an entry, its key written as a `.pub` file holds it. `spwn devices forget <name> --confirm=<name>` takes one away. `add` and `forget` are the engine's calls, each one line of the journal, and this Mac's engine is the book's only writer: a terminal's `add` or `forget`, and a frame any server of this Mac serves (`guest serve --stdio`, `engine attach`), are run by the engine over its socket, the far mark riding with them. With the engine down both are refused, with `station engine start` as the hint, and nothing is written.
4. **`add` asks the owner's presence, every time**, with a reason that names the device and its key's fingerprint, never riding the engine's open key session. Refused or absent, nothing is written. `add` is refused when a transport marked the request far (`devices.add-here-only`): `engine attach`, so `--on` too. A shell on the Mac is not marked: a device whose key opens this Mac's sshd can run `station devices add` there, or `station guest serve --stdio`, and is recorded as local, so the presence `add` asks is what stops it. No mark is given to `guest serve --stdio` on a Mac: the same shell runs `station devices add` with no door at all, so the mark would stop nothing.
5. **`forget` asks no presence, signs nothing and works from afar.** Taking trust away is the safe direction, and a headless Mac must be able to drop a stolen laptop at once, even with no key session open. What it cuts today is a new login with that key into this Mac's VMs. It does not end an ssh session already open into a VM, which outlives the guest's rewrite of its keys, and it never touches this Mac's own `~/.ssh/authorized_keys`, so a key listed there still opens this Mac through its sshd, and from this Mac its VMs, through the image key and `agent.sock`. Its words say so; ending the open sessions is the door's.
6. **A frame from another machine is marked by the transport that carried it.** A server that serves another machine's frames (`engine attach` today) marks every frame it reads as far, and the mark rides every hop after it: another Mac's engine socket, and the hop into a VM's guest, which carries the session (`by`) too. A frame may set the mark, never clear it, so a local process that leaves it out gains nothing: it still meets presence.
7. **Each entry is sealed by this Mac's device key, and the book is anchored.** The seal signs `spwn-device-book/v1`, this Mac's name, the SHA-256 of this Mac's device public key, then the entry's name, key, sorted channels and added time, one per line. Each read checks it against the public key of the device key the process holds, the Enclave's, never against `device-key.pub`. A seal alone says nothing of the book's state: an old copy of the file holds entries whose seals all verify. So every `add` and `forget` raises the book's generation, up to 2^53, where it stays (a head above it is one Spwn never writes, so a planted generation cannot overflow the next write), and this Mac keeps the head, the generation and the SHA-256 of the book as written, in its login keychain (the item `station-devices`, beside the vault's items), through `/usr/bin/security`, never one a PATH names, as the vault does; only the spec build reads that path under `STATION_SYSTEM_ROOT`, which the release build ignores for the vault and the head. The head is written before the file.
    - A book that is not the anchored one (an old copy written back, a book from another Mac or written by hand, or a write cut between the keychain and the file) is trusted as a whole nowhere: no entry of it reaches a VM, the read says `stale` and gives each entry the command that adds it again, and the next change starts from an empty book. A keychain that cannot be read trusts no entry. A write cut between the two writes therefore fails closed, at the price of the book.
    - An entry whose seal fails in an anchored book, as after [ADR-085](085-a-mac-run-alone-keeps-a-device-key-that-signs-with-nobody-present.md)'s key swap, reaches nothing either, and adding it again replaces it.
    - The engine reads the book and the keychain once, when it starts, before it serves, and from then on believes only the books it wrote itself: a book or a keychain head it did not write, at any generation, rolled back or moved forward, is not the anchored one. Nothing of it is trusted, no VM is given its keys, and the next `add` starts from an empty book. Any other process of this Mac takes the head the running engine holds, through its `hello`, and reads the keychain itself only when no engine answers or the engine's `hello` carries no head.
    - The start read is final even when it fails. A book that cannot be parsed, or a keychain head Spwn never writes, leaves the engine holding a head no book has: it trusts nothing until its own next write, which starts from an empty book whatever the file holds and anchors that book, or until it restarts. A keychain that cannot be read at all (locked, or `security` refusing) leaves it waiting: the engine reads the keychain again at each read of the book, only until a read first answers, a head or none, and never after. The engine keeps in memory the SHA-256 of the book it found at its start and that book's head; the first answer is held only if it is that head and the file is still, byte for byte, that book. Any other answer leaves the engine holding a head no book has, as above: a head written into the keychain before or during the wait, and a book written meanwhile, are trusted nowhere until the engine writes.
    - Why the wait is safe against a process that controls the timing: such a process can lock the keychain (`security lock-keychain` asks no password) and kill the engine, which launchd starts again, but it cannot unlock the keychain, and the wait holds no head but the one of the book that was on disk at that start. Planting a book and its head together before a restart is the restart's own weakness ("What the seal is worth"), so the wait adds no way in; a head planted without its book, and a book planted while the engine waits, are refused until the engine writes.
    - Why it waits rather than refusing: the engine is a launchd agent of the owner's session (`RunAtLoad`, `KeepAlive`), which macOS starts after the login unlocks the login keychain, so at login the read answers (not proven on a real Mac). A locked keychain at a start is the benign case of a restart after the keychain locked, on its timer or by hand, or of a keychain whose password is not the login's; the finding then blames no one and ends on its own once the keychain answers.
    - A book the engine trusts nothing of raises the finding "The device book changed outside Spwn", on `spwn devices`, on Home and in the menu bar's needs: it says what was found, that nothing of it is trusted, and the gesture that repairs, each device added again, the owner at this Mac, its key taken from the device itself, never from the book, which `devices --json` therefore gives no key for a broken entry. A book of at least one device that the engine waits to check raises "The device book is not checked yet" instead (an empty one lets no one in, and raises nothing), red too, which names the keychain to unlock; `spwn devices` then refuses with the keychain's own error. Either finding lasts until the engine writes a book or restarts, the second also until the keychain answers.
    - A VM loses a book's keys at the engine's next walk of it, not at once; with no engine running, a VM keeps the last keys it was given. The engine records the keys a guest was given once their hello is written to it, so a hello whose write failed is sent again at the next walk.
    - The head carries no seal of its own: `forget` would then have to sign, and could not on a present-owner Mac with no key session open. The anchor pins the exact entry set, so a head seal would add no property.
    - A book written before the anchor (DB0 to DB9) has no generation and no anchor, so it is stale like any unanchored book. No user has one, and no code reads it otherwise.
8. **The key agent signs logins only.** It signs an SSH user authentication request (RFC 4252 §7) for the key it serves, and for a relayed key alike, and refuses any other data, so `agent.sock` cannot forge a seal. An SSHSIG (`ssh-keygen -Y sign`, git's ssh signing) through it is refused too: nothing points a shell's `SSH_AUTH_SOCK` at `agent.sock`, and the `git-signing` setting signs with GPG. A connection that binds a forwarded session (`session-bind@openssh.com` with `is_forwarding` set) signs nothing. A client older than OpenSSH 8.9 sends no binding, so its forwarded agent is told from a direct one by nothing; it still signs logins only.
9. **Of the keys the Mac hands a VM, it trusts its Mac's device key and the book's entries that carry `pipe`.** Two keys outside the book open the VM too, and stay: the image key (`images/key`, `station-image`, [ADR-077](077-a-workspace-trusts-its-macs-device-key-first.md)), and any key the `authorized-key` setting writes into the VM. The device key's line is drawn from the key the engine holds, never read from `device-key.pub`, which stays an export the blocks name for ssh. The copy of the Mac's `~/.ssh/authorized_keys` and the `~/.ssh/id_ed25519.pub` line leave. The engine sends the new keys to every guest connected to it as soon as `add` or `forget` ends, and any other guest gets them in the hello of its next connection.

### What the seal is worth

- On a Mac with a present owner, a seal the engine's device key makes takes a Touch ID. A process that runs code as the owner needs none to forge one: it makes a Secure Enclave key of its own with no access control and writes its blob as `device-key.enclave`, which the engine loads without checking its access control, so after the next engine start that key is this Mac's own, and every seal it makes holds. That flaw is [ADR-085](085-a-mac-run-alone-keeps-a-device-key-that-signs-with-nobody-present.md)'s, older than the book, and its own security lot in TODO.
- On a Mac run alone, ADR-085's key signs with nobody present, and any process of the owner on that Mac can load its blob. There the seal guards against accidents only: a sync tool, a restore, a hand edit.
- The anchor is worth what the login keychain is. A writer of the state folder alone (a backup restored, a sync tool, a process confined to files) cannot roll the book back. A process that runs `security` as the owner is taken to be able to, on any Mac: the item is made by `security` with no `-T`, so its access list should trust `security` itself, as for the vault's items (not verified on a real keychain). Short of the key swap above, it forges no seal on a present-owner Mac, but it can write a book of any mix of entries this Mac ever sealed, a forgotten device's included, with the head that anchors it: a seal covers its entry alone, and the head is a plain SHA-256. While the engine runs that book is trusted nowhere, and raises the finding above. Across an engine restart it is trusted: the new engine has only the keychain to start from, and a book and a head written together while no engine ran, or before a restart the process caused, read as the anchored ones. Closing that needs a head no `security` call can write, in TODO. On a Mac run alone that process can forge a book outright, so there the anchor too guards against accidents only.
- The engine's socket, `engine.sock`, is made mode 0600 in a state folder set to mode 0700 before the bind, and the engine closes at accept any peer whose uid is neither its own nor root's (`SO_PEERCRED` on Linux, `LOCAL_PEERCRED` on macOS), so another user of the Mac reaches none of its calls; every unix socket station serves (`agent.sock`, a guest's) is made the same way. Same-user code can still stand in the middle by replacing the socket path: only the engine's own trust decisions are protected, not what a surface shows the owner.

### Amendments

- **ADR-090.** The gesture is `spwn devices add`, not `spwn devices allow`. `hello` is no channel: the first frame of `spwn-api` is already `hello` ([ADR-016](016-api-v2-and-remote-by-api.md)), and ADR-074's budget is measured on it. The door's channels are `spwn-api`, `pipe` and `herdr`, the book's.
- **ADR-077.** Its VM half leaves: the `authorized_keys` copy and the personal key line. A key in a Mac's `authorized_keys` no longer opens its VMs by itself; a login into the Mac still reaches them, through the image key and the engine's socket, as ADR-077 found.
- **ADR-085 §4.** The engine's hello sends the line of the key the engine holds, not the line `device-key.pub` holds; the engine start still writes that file, as an export.
- **ADR-064 §4.** The `id_ed25519` line leaves guest trust. The relay of the owner's key does NOT leave with the book: until the door, another Mac is still reached through OpenSSH, whose far sshd reads its own `authorized_keys`. The relay leaves with the door's cut.

## Consequences

- After this lands, another Mac's ssh to this Mac's VMs is refused until the owner runs `spwn devices add <that mac> <its key>` here, with presence. The empty book's hint says so. No compatibility path is kept.
- The book never writes a Mac's `~/.ssh/authorized_keys`: Mac-to-Mac through OpenSSH is unchanged until the door turns that sshd off.
- A VM block that still offers `~/.ssh/id_ed25519` costs one refused attempt after the device key; the held branch `fix/ssh-device-key-only` removes it.
- On a present-owner Mac, `add` can show two sheets in one gesture: the presence it asks, then the Enclave's own when the engine's key session is not open yet to sign the seal.
- Open: whether the presence sheet of `add` on a Mac with no screen, answered through a remote desktop, is acceptable to the owner.
- Open: `add` from a terminal asks presence from the engine's process, as the window's grants do; that its sheet shows from the engine's launchd job on a real Mac is not proven.
- Open: the real Enclave signing a seal, a real guest sshd accepting a book key, and the real login keychain keeping the head (`security` from the engine's launchd job, a locked keychain) are not proven by the suites, which run the device-key, presence and keychain fakes.
- Not done: the plan's rule that `add` refuses the image key (`images/key`, trusted in every VM as `station-image`) or a key a VM holds. Today such an entry grants a VM login that key already has, or that the book's `pipe` gives anyway; it matters once `spwn-api` and `herdr` open anything, so it is the door's, in TODO.
