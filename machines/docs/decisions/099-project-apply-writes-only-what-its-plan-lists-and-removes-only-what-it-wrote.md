# ADR-099: `project apply` writes only what its plan lists, and removes only what it wrote

**Status:** Proposed
**Date:** 2026-11-26

Builds on [ADR-088](088-agents-live-in-the-one-binary-as-families-reached-by-calls.md): the project family is a family of the engine, reached by its calls. Root [ADR-021](../../../docs/decisions/021-one-program-spwn-one-command-for-everything.md) rule 5 gives a project's `spwn.yaml` its `plan`, `apply` and `drift`; it does not name `spwn build`, which the programme's lot A2b3 deletes. This record says what replaces its render.

## Context

`spwn build --tree-only` wrote an agent's rendered tree into an output folder, and with `--force` emptied that folder first, whatever it held. Its default built a Docker image from the tree. On a machine, an agent runs in a run folder of the project's gitignored state, `.spwn/agents/<agent>/`, with links into its Mind beside the rendered files, so a writer that empties the folder would delete what it never wrote. `project plan` already rendered each agent in memory to judge it; a second render path for the write could disagree with it.

## Decision

1. **One Render hook.** The contract `Projects.Render(root, agent)` returns an agent's files, each a path, its bytes, its mode and whether it is a link; it writes nothing. Both `project plan` and `project apply` compute their changes from it through one pure function, `project.ChangesOf`, so what a plan lists is what an apply writes.
2. **The harness is declared.** An agent renders for its own `runtime.backend`, else the project's, else the catalog's first harness; never one picked by a sign-in.
3. **A record of what was written.** Apply keeps the digest of each file it wrote in `.spwn/applied.json`. A file it wrote and the declaration no longer renders is removed; a file it never wrote and that is not rendered is never read nor touched. A file it never wrote at a path it renders is read, and named as changed by hand before it is overwritten, so the same question as decision 4 is asked. The record is a file of the repository, so a path it holds outside an agent's run folder is never read nor removed. An apply stopped by a change it could not make keeps the record of the changes it made, and the next one starts where it stopped.
4. **A confirmation follows its consequence.** An apply that only adds asks nothing. One that overwrites or removes names each file, a file whose digest is not the record's as changed by hand, and asks once, yes or no; off a terminal and with `--json` it refuses without `--yes`. A plan with an error writes nothing. A second apply writes nothing.
5. **No image.** Apply builds no image and starts no agent.
6. **No link is followed, and the declaration cannot reach a file outside the project.** Neither the declaration (`spwn.yaml`, `spwn.lock` and everything under `spwn/`), nor the run folders, nor the record is reached through a link. Before any of the declaration is read, show, plan, drift and apply walk it one name at a time: a link there is refused, naming it, and so is a name that is neither a file nor a folder, a FIFO say. Then each read of the declaration goes through a root opened at the project's folder (the root module's `platform.Tree`, over Go's `os.Root`), so no name or path the declaration gives can direct a read elsewhere: an agent's name, a `knowledge:` path, an `@`-import, a dependency, a watch path. A path that leaves the folder by `..`, by an absolute path elsewhere or by a NUL is refused by its name alone, before anything there is opened or asked to exist; a link swapped in after the walk whose target is outside is refused by the root; and a read opens only a file or a folder, never waiting on a FIFO. Where the declaration names such a path, the plan says so as an error of its field, "leaves the project" (`project.invalid`): an agent that is not one folder name of `spwn/agents/`, a `knowledge:` path outside the project (the world's knowledge is a folder of the project), an `@`-import whose every candidate is outside; a dependency named `..` is invalid; a watch path outside the project is an advice that it is not checked, as the watcher reads it when the world runs. The issue is the same whether the outside path is there or not. A declaration is what a harness renders for a model provider, and a cloned repository could otherwise have a file from outside the project copied into it. A hard link in the declaration is read as the file it is: it brings no byte the repository did not hold. Apply reaches every path of `.spwn/` the same way: a link on a folder of a run folder's path, or on `.spwn/applied.json`, is refused by plan and apply, naming it, before anything is written. A link a harness renders is written as a link, and a link at a rendered file's name is replaced, never written through. The project's root itself may be a link: it is the folder the owner named, every path is reached from it, and an absolute path through the folder it resolves to is a path of the project. `project create` makes its new folder with one mkdir, which fails on any name already there, a link included, and writes each file of the scaffold or the example from the folder that holds it, reached the same way, so a link swapped in at the new folder's name or under it after the mkdir is refused, never written through.

## Consequences

- R1a's `agents start` renders through the same hook into the same folder; the links to the Mind are more files of the hook's answer, so neither its signature nor the writer changes.
- `spwn build`'s `--output`, `--force`, `--agent` and `--runtime` have no successor: the folder, the scope and the harness are the declaration's.
- Drift does not yet tell a file changed since apply; plan and apply say it, as `changed by hand`.
