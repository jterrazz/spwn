# ADR-087: A fetched macOS guest takes its key at its first login

**Status:** Proposed
**Date:** 2026-11-23

Amends [ADR-084](084-base-macos-is-fetched-from-cirrus-labs-pinned-by-digest.md).

## Context

ADR-084 fetches `ghcr.io/cirruslabs/macos-tahoe-base` as Cirrus Labs made it. That image holds one account, `admin`, whose password is the default Cirrus Labs gives every image, `admin`, and no key of Machines. The engine reaches every VM as the VM user by the image key, and the owner's `ssh` by the device key the guest writes in its keys block (ADR-064, ADR-077, ADR-085). Neither is in a fetched macOS guest. On the new Mac mini on 2026-11-23 (acceptance pass 5), `station machines create macos-test --image base-macos` always ended `Failed at SSH 4 of 4`, the engine's log reading `ssh: unable to authenticate, attempted methods [none publickey]`. Its hint, `station machines start macos-test`, answered `is already running`, and the row stayed failed.

A Linux base is plumbed while it is built: `linux.sh` runs once over the base's `admin` password, adds the user and the image key, turns password login off, and the cleanup removes `admin` (ADR-044, ADR-051). A fetched image has no build to run that in. Three ways to put the key in were weighed:

- **A tart feature.** `tart run --dir` shares a folder with the guest, but a macOS guest mounts it only after a login, and something inside must still copy a key from it. tart has no cloud-init for macOS guests.
- **The guest agent's path.** The engine sends the keys in its hello to `station guest` inside the VM (ADR-077). That path needs the engine to be connected already, the very thing missing.
- **One login by the published default.** The same login `images build` already makes to a Linux base (`baseAdmin`, `admin`/`admin`), run once per VM, then retired.

## Decision

1. **A fetched image's VM is locked down at its first login.** When the engine's dial by the image key is refused (or this Mac holds no image key yet) and the VM's image carries a lockdown (`catalog.Image.FirstLogin`, `base-macos` alone), the engine makes the image key if it is missing and logs in once as `catalog.UpstreamLogin` (`admin`/`admin`, a public constant of every Cirrus Labs image, never a secret of the owner's). There it makes a private folder (`mktemp -d`, mode 700, owned by the login), puts this Mac's own station binary and `apps/engine/catalog/images/macos-firstlogin.sh` in it, and runs the script as root from that file, its values (the VM user, the image key's public line, the login, the binary's SHA-256) on stdin, never in a command line. The script reads them, then closes its stdin. It goes on only when the binary's hash is the engine's, and removes the folder when it exits; a run killed outright (`SIGKILL`) leaves the folder behind, and it holds no secret: the binary, the script, and nothing of the values. The engine then dials by the image key again.
2. **The image's login is closed first, the key is reachable last, and a marker says the lockdown finished.** The script is idempotent, and its order is the guarantee. It removes its marker (`/var/db/station/locked`) first, checks the binary, then the VM user: it refuses one the rule of `vm_user` refuses (Consequences), the image's own account (`admin`) or `root`, before any change, so that refusal leaves the image as it was, as a refused binary does, and the engine stops the VM (§5). Its first change closes everything the image's login opens: it writes `/etc/ssh/sshd_config.d/000-station.conf` (no password or keyboard-interactive login, no root login, `AuthorizedKeysFile .ssh/authorized_keys`), which every new connection reads; removes the auto-login and `/etc/kcpassword`; turns Screen Sharing off (`launchctl disable` then `bootout` of `system/com.apple.screensharing`) and removes `/Library/Preferences/com.apple.VNCSettings.txt`, a VNC password's file; gives `admin` a password made there (`dscl . -passwd` by the old one, which macOS requires of root for an account holding a secure token), unless `admin`/`admin` already fails; empties `admin`'s and root's authorized keys; and removes `admin`'s passwordless sudo (`/etc/sudoers.d/admin-nopasswd`). Only then does it set the guest up. It makes `/usr/local/bin` `root:wheel`, mode 755, and installs the binary there, `root:wheel`, 755. It makes the VM user, an admin, or keeps an existing one, and gives it either way a new password made there, a passwordless sudo and an empty `~/.ssh/authorized_keys`; the sudo rule is written to a file sudo skips (its name holds a dot), `root:wheel` 0440, checked by `visudo -cf`, then moved into place. It gives the image's Homebrew to the VM user (`chown -R` of `/opt/homebrew`, when `admin` owns it), since `brew` writes its prefix as the user who runs it, and `admin` logs in no more. In a fresh clone of the pinned `macos-tahoe-base` (2026-11-23), `/usr/local/bin` was already `root:wheel`, mode 755, and `/opt/homebrew` `admin:admin`; in a clone of the gates' base, built from Cirrus Labs' `macos-tahoe-xcode`, `/usr/local/bin` was `admin:wheel` and every entry under `/opt/homebrew` `admin`'s; after the lockdown, `root:wheel` and the VM user's in both. The same fresh clone served Screen Sharing: `com.apple.screensharing` enabled, launchd listening on TCP 5900, which takes `admin`'s password; it held no `VNCSettings.txt`. It removes the image's host keys and makes the guest's own (`ssh-keygen -A`), and prints the new ed25519 one at once, its stdout carrying nothing else; the engine replaces every key the VM's known hosts held with it once that line came, whether the lockdown then ends 0, fails, or its session drops or outlasts its 3 min, so the next dial checks the guest's own key. It then checks all of it: `admin`/`admin` refused, no `kcpassword`, Screen Sharing not loaded, no `admin` sudo rule, `sshd -T` reading each line, the VM user's sudo. Only then does it write the image key, as the VM user's only authorized key, and its marker, its last step. A run cut before its first change leaves the image as it was. One cut inside that block may leave part of the image's login: sshd takes no password from its first line on, but until `admin`'s password is changed, `admin`/`admin` still opens a local login and `su`, and Screen Sharing until it is turned off, just before. One cut after the whole block leaves no login of the image's, and a guest the key does not open until the key is in. The marker guards against an interrupted run, not against an attacker: whoever holds root in the guest can write it.
3. **A key dial is trusted only with the marker.** After every dial by the image key to a VM whose image carries a lockdown, the engine reads the marker (`test -f`). When it is absent (a lockdown cut between its key and its marker), the engine runs the same lockdown again over that session, as the VM user by its sudo, and keeps the connection only once it exits 0. No session is opened on a guest whose lockdown did not finish.
4. **A start of a VM whose create failed is its retry even while it runs.** `machines.start` answers `is already running` only for a VM whose create did not fail; one that runs with a failed birth is run (a no-op), waited for and set up as ADR-062 §3 says, so the hint a failed create gives is a gesture that can succeed.
5. **A VM whose lockdown fails is stopped at once, and its lockdown runs once per start.** When the lockdown cannot run (the VM user refused, the image's login refused too), fails, or does not finish in 3 min, the engine stops the VM, keeps its wish stopped, and dials it no more; why stays with the VM until its next run, and the create (or the start) fails at SSH with that cause as its own, kept as the failed birth's cause (ADR-062 §1). The engine first tries both the key and the image's login: when the guest takes neither, or answers with a host key other than the one pinned, the cause says so, and the hint is `station machines delete <vm>, then make it again`, since no start can run the lockdown, and the failed birth keeps it (`gone`), so its Needs you row offers `station machines delete <vm>` and the window no Try again, its Delete alone; otherwise the hint is ADR-062's, and the start runs the lockdown again, once. This departs from ADR-062, which keeps a VM whose create failed as it is, running when it ran: a Linux VM failing SSH holds nothing open, while a macOS guest whose lockdown stopped short may still take `admin`'s published password, with root behind it, for as long as it runs, and every redial (each 30 s) would run the whole lockdown again.

## Consequences

- **The VM user is checked before any VM is made, by one rule.** The VM user is `vm_user` when `preferences.json` sets it, else the Mac's account. One rule judges both, `machines/contract.CheckVMUser`, its pattern `VMUserPattern` (`^[a-z]([a-z0-9_.-]{0,30}[a-z0-9_-])?$`), and it is never `admin` nor `root`; the [Preferences](../reference/preferences.md) reference states it for the owner. It takes what both a macOS short name and a Linux user name take: the dot, which macOS short names hold (the owner's Macs use `jterrazz.ops` and `jterrazz.agent`) and `useradd` takes (probed on 2026-11-23 on Ubuntu 24.04, shadow 4.13, and Debian trixie, shadow 4.17, which also take an uppercase letter and a dot last, both refused here); lowercase only, since macOS reads a user name whatever its case (in a fresh clone of the pinned image on 2026-11-23, `id Admin` answered `uid=501(admin)` and `dscl . -authonly Admin admin` succeeded), so `Admin` would have passed a plain comparison and been given `admin` itself; no newline, which would shift the values the script reads. A create, an image build, and the start or restart of a VM whose image carries a lockdown, refuse a name the rule refuses before any VM is made or run, the hint `set vm_user in ~/.config/station/preferences.json` (`set another vm_user` for a `vm_user` set), and make nothing; `station init` writes this Mac's account as `vm_user` only when the rule takes it, and says so when it does not. Every other use of the name takes it only once the rule has: `machines ssh` to a VM of this Mac refuses it with the same hint, the `~/.ssh/config` blocks are not refreshed while it is refused (the list says why, and the file keeps the last blocks it was right about), and the engine dials no VM as it (`GuestTarget`): a VM it is refused for that still runs says so in the list and on its page, `is unreachable: <mac>'s VM user is one the rule refuses`, the hint `set another vm_user in ~/.config/station/preferences.json`, never a restart that cannot help. A `preferences.json` that cannot be read is the read's own error at each of these uses, never a refused name: an image build stops on it rather than taking this Mac's account, and a dial that meets it is the dial's own failure, tried again, so a running VM is not stopped for it. Beneath the rule, the ssh command station prints single-quotes a user or host that is not one plain word and refuses one starting with `-`, which ssh reads as an option even quoted (`catalog.SSHCommand`); the ssh config writer refuses a block whose name, user or Mac is not one word of letters, digits, `.`, `_` and `-`, or starts with `-` (`contract.Unwritable`); and `machines ssh` takes every user and host it prints by that same rule, so a Mac's user written into `preferences.json` by hand, which `machines add` never wrote, is refused there too, by every command that names that Mac, and by every list, which leaves the Mac out, never asked, and says why under Needs you; the ssh line to another Mac's engine (`sshstdio.Argv`) and the unlock's put `--` before the Mac, and the first refuses a name the rule refuses before any ssh runs: no name reaches a shell or a config line as more than one word, nor as an option. That `--` is the only one, since OpenSSH reads no option after a destination it follows, and a test runs the real client against a sshd of its own to prove the far side is given exactly `sh -c <line> station engine attach`. A Mac's `key` that ssh_config would read apart and a `lan` that is no IP address nor DNS name are refused the same way, never written to `~/.ssh/config` nor to `-o HostName`, and a VM or Mac name never starts with `-`. The lockdown checks it again, in the engine (`GuestTarget` and `LockdownOf`, a lockdown failure only for a name the rule refuses, a `BadVMUserError`, for a VM it dials by itself: a VM user changed to a refused name while the VM runs stops that VM at the engine's next dial, nothing run in it) and in the script, by the same pattern, which `catalog/images_test.go` pins to the contract's. The script's check comes before its lock: on the new Mac mini on 2026-11-23 (acceptance pass 6), the Mac's account `jterrazz.ops`, taken as the VM user, was refused by a script that checked it after its lock, so every macOS guest made there lost the image's login and never took the key. A refusal before the lock leaves the image's login open, as a refused binary or a run cut before its first change does, and the engine stops the VM at once (§5); the start that follows refuses the same name before it runs the VM, so the guest runs with that login open only until the lockdown fails, as in any failure before the lock. An account the guest holds of its own is never a VM user either: the rule refuses a leading `_`, which names macOS's own accounts, and each guest script refuses, before anything else changes, a VM user that is an existing account of a system uid, the macOS lockdown one under 500 or above 60000, the Linux plumbing (`linux.sh`) one under 1000 or above 60000. The rule before it took a leading `_`, so a VM user starting with `_` that it took is refused now, and a VM still running under one is stopped at the engine's next dial. A script that skipped making an account `id` found would otherwise give that account a password, sudo without one and the image key in its home: in a fresh clone of the pinned image on 2026-11-24, `daemon` is uid 1 with `/var/root` for its home, and `nobody` uid 4294967294, which a check of "under 500" alone let through, the lockdown then running whole as `nobody`; on Ubuntu 24.04 and Debian trixie, `daemon` is 1 and `nobody` 65534. The uid is the guard, not a list of names, so any account of a release to come is refused alike; the account a converged run made, at 501 or above on macOS and 1000 or above on Linux, passes, so a run again over the key converges. Another name of the image's own login is that login by its uid, so each script also refuses, before anything else changes, a VM user whose uid is that login's: the lockdown `admin`'s (501), `linux.sh` that of the base's `admin`, the build's login its cleanup removes. In a fresh clone of the pinned image on 2026-11-24, `admin` holds one RecordName and the RealName `Managed via Tart`, which `id` resolves to 501 too and the rule refuses (a space, capitals); a second RecordName added to `admin` passed the name check and the system-uid check, and only the uid of the login refuses it. macOS refused a second record of uid 501.
- Footprint in the guest: one admin account named as the Mac's VM user, `/etc/sudoers.d/60-station-user`, `~/.ssh/authorized_keys` and `~/.config/station/` under its home, `/usr/local/bin/station`, `/etc/ssh/sshd_config.d/000-station.conf`, `/var/db/station/locked`, and Screen Sharing disabled. `admin` stays, with a password nobody holds, no authorized key, no sudo rule of its own and no auto-login, so the guest has no logged-in desktop after its next reboot. On the Mac: the image key, made at the first macOS VM when no build made it before.
- `admin`'s passwordless sudo is removed rather than kept: nothing of station's runs as `admin` once the lockdown ran, and a rule nobody needs is one an account recovered later would inherit.
- **The host key is trusted on first use, and that first use is weak.** A clone of the Cirrus Labs image serves the host keys baked in it, the same in every clone and readable by anyone who pulls the image (seen on 2026-11-23 in a fresh clone of the gates' base made from it: host keys dated 18 August, the image's day, not the clone's). The first login pins that key, accept-new, so it authenticates nothing: whoever sits between the Mac and the guest in the open window (below) can answer it. The new host key the lockdown prints travels over that same session, so it is as trusted as that session is, no more. Past the lockdown, every dial checks the guest's own key, and a guest answering with another is refused. A stronger first contact would take a channel off the network, such as tart's guest agent over virtio, which the Cirrus image runs; it is not taken here. A lockdown whose session drops before its print reached the engine leaves known hosts holding the old key. A dial to a VM whose image carries a lockdown that meets a host key other than the one pinned is a lockdown failure no start can cure, whenever it comes: the engine stops the VM and says `station machines delete <vm>, then make it again` (the probe of both logins after a failed lockdown counts such a dial as refused); nothing deletes it but its owner.
- **The open window.** From the clone's boot, the guest takes `admin`/`admin` over ssh until the lockdown's first change, by Screen Sharing until the lockdown turns it off, and by a local login and `su` until its password change, a few lines later; `admin` has root by its passwordless sudo. Who can reach it then: anything on this Mac, every other VM on its vmnet NAT network (`192.168.64.0/24`), and, for a workspace made `--network bridged`, the whole LAN the Mac is on. The engine dials as soon as sshd answers, and a lockdown that fails within the window stops the VM, which closes it. Anyone who reaches it in that time holds root, and nothing the lockdown does afterwards can undo an implant made with root; it resets the entry points it knows (both accounts' passwords and authorized keys, root's authorized keys, the sudo rules, sshd's configuration), nothing more. A bridged workspace is not made on the NAT first and bridged after its lockdown: its network is fixed at its run, so that would cost a stop and a second boot of every bridged macOS workspace, and the reach it closes is the LAN's for that window; the trade is the owner's to revisit.
- Passwords on a command line: the VM user's goes through `dscl`'s stdin. `admin`'s cannot: `dscl` asks the old password of an account holding a secure token from a terminal only, and fed through a pseudo-terminal it works only with timed pauses (probed on macOS 26.6.2, 2026-11-23). `sysadminctl -addUser` takes a new account's password only as an argument too (`-password -` needs a terminal); that one is replaced at once through `dscl`'s stdin. Each appears for an instant in a root command line inside the guest, readable only by what already runs there, which in that window holds root through `admin` anyway.
- **Homebrew is on the PATH of station's lines, and of a login shell.** Station's delivery lines run under `catalog.GuestPath`, which holds `/opt/homebrew/bin` beside `~/.local/bin`, as it does on a Linux guest. A login shell in the guest (the owner's `ssh <vm>`) finds `brew` by the image's own `/etc/paths.d/homebrew`. A bare `ssh <vm> <command>` runs a non-login zsh, which reads neither, so it does not find `brew`: a known limit (probed in the fresh clone: `zsh -lc 'command -v brew'` found it for a new user, `zsh -c` did not).
- The guest's station is the binary of the Mac's engine when the VM was locked down. A newer engine does not replace it; the Linux images' baked binary is in the same case.
- What is proved over the fake world, where a guest plays its lockdown and the world cuts it (`world lockdown-cut before-lock|before-key|after-key|never-ends|drops-after-print`): the key dial refused, the first login as the image's account, the lockdown run from its folder, the marker read, the create made; a lockdown cut before its lock stops the VM, and its start runs the lockdown again by the image's login; one cut after its key stops it, and its start runs it again over the key; one cut between its lock and its key, one that never finishes, one whose session drops once it printed its host key (the VM repinned to that key), and a first login refused too stop it, told to be made again, the lockdown run once per start; a locked-down VM answering another host key at its start is stopped, told to be made again; a `vm_user` that is `admin` or `Admin`, and a Mac account the rule refuses with no `vm_user` set, are refused before any VM is made; a Mac account holding a dot (`jterrazz.ops`, the world `dotted-account`) makes its workspace, its ssh block's user that account; a start for an account the rule refuses runs nothing; the world's guest refuses, before its lock, a VM user the script refuses; a running VM whose create failed is retried by its start; a fetched macOS workspace the engine dials while `preferences.json`'s `macs` does not parse keeps running, its single lockdown run as it was; a build under a `vm_user` that does not parse is refused with the read's error; a running Linux VM refused for its VM user is listed, and paged, with that cause and the hint `set another vm_user`; `machines ssh` refuses a hand-edited Mac user that is no ssh word or starts with `-`, for that Mac and the VMs it holds. The cause reaches the create's error and the failed birth's cause. What is not proved over it: the engine's wait for a dial still in progress past its 60 s (`dialWait`), which a real lockdown needs. The script's order, its VM user's check before its lock among it, is pinned by `catalog/images_test.go`, and its pattern to the contract's by `machines/calls/firstlogin_test.go`. The script ran on a real macOS 26.6.2 guest (a throwaway clone of the Cirrus Labs base: killed after its whole lock block, before the VM user's check, `admin`/`admin` was refused over ssh, `dscl . -authonly admin admin` refused too, and `sshd -T` read password login off; `admin` as the VM user was refused; the full run took 8 s; run again over the key). Again on 2026-11-23, in a fresh clone of the pinned `macos-tahoe-base` (macOS 26.6.2, 25G83): `Admin` as the VM user was refused, by a script that then checked it after its lock; a run killed right after its print printed one line, the key the guest then served, and left neither `admin`/`admin` (over ssh or `dscl . -authonly`) nor the key working (the engine's repin of that very line is `TestARepinTakesTheLineARealLockdownPrintedBeforeItWasKilled`, the drop by the fake cut `drops-after-print`); a full run over it then converged, Screen Sharing disabled and nothing on 5900, the VM user in by the key, `brew` found under `catalog.GuestPath`; In a third fresh clone of it the same day, with the check before the lock: `Admin`, `admin`, `root`, `jterrazz.`, `Jterrazz.ops` and none were each refused in under 3 s, and after each the image was as it was (`admin`/`admin` over ssh and `dscl . -authonly` taken, no `000-station.conf`, `kcpassword` and the auto-login there, Screen Sharing loaded, `admin`'s sudo rule there, `sshd -T` reading password login on); `jterrazz.ops` then converged in 15 s (uid 502, `/opt/homebrew` its own, its sudo rule `jterrazz.ops ALL=(ALL) NOPASSWD:ALL` read), its key login answered `jterrazz.ops`, its sudo and `sw_vers` (26.6.2, 25G83), and the run again over its key converged. Again on 2026-11-24, in a fresh clone of the pinned image (26.6.2, 25G83), with the check of the login's uid: a second RecordName of `admin` (`adminalias`, uid 501) was refused, the image as it was, where the script before that check went past it; `jterrazz.ops` then converged from the untouched image in 7 s, and twice again over its key. `linux.sh` ran in throwaway `ubuntu:24.04` and `debian:trixie` containers the same day: two other names of `admin` (a second passwd line and a `useradd -o`, uid 1000), `daemon` and `nobody` were refused with nothing changed, and `jterrazz.ops` converged three times. `ssh <vm>` by the device key on a real Mac is one acceptance run after the train, a macOS guest nesting no VM (`kern.hv_support` is 0).
- ADR-084's `admin` "with a known password" holds for the image, no longer for a VM made from it.
