# ADR-087: A fetched macOS guest takes its key at its first login

**Status:** Proposed
**Date:** 2026-11-23

Amends [ADR-084](084-base-macos-is-fetched-from-cirrus-labs-pinned-by-digest.md).

## Context

ADR-084 fetches `ghcr.io/cirruslabs/macos-tahoe-base` as Cirrus Labs made it. That image holds one account, `admin`, whose password is the default Cirrus Labs gives every image, `admin`, and no key of Machines. The engine reaches every VM as the VM user by the image key, and the owner's `ssh` by the device key the guest writes in its keys block (ADR-064, ADR-077, ADR-085). Neither is in a fetched macOS guest. On the new Mac mini on 2026-11-23 (acceptance pass 5), `station machines create macos-test --image base-macos` always ended `Failed at SSH 4 of 4`, the engine's log reading `ssh: unable to authenticate, attempted methods [none publickey]`. Its hint, `station machines start macos-test`, answered `is already running`, and the row stayed failed.

A Linux base is plumbed while it is built: `linux.sh` runs once over the base's `admin` password, adds the user and the image key, turns password login off, and the cleanup removes `admin` (ADR-044, ADR-051). A fetched image has no build to run that in. Three ways to put the key in were weighed:

- **A tart feature.** `tart run --dir` shares a folder with the guest, but a macOS guest mounts it only after a login, and something inside must still copy a key from it. tart has no cloud-init for macOS guests.
- **The guest agent's path.** The engine sends the keys in its hello to `station guest` inside the VM (ADR-077). That path needs the engine to be connected already, the very thing missing.
- **One login by the published default.** The same login `images build` already makes to a Linux base (`baseAdmin`, `admin`/`admin`), run once per VM, then retired.

## Decision

1. **A fetched image's VM is locked down at its first login.** When the engine's dial by the image key is refused (or this Mac holds no image key yet) and the VM's image carries a lockdown (`catalog.Image.FirstLogin`, `base-macos` alone), the engine makes the image key if it is missing and logs in once as `catalog.UpstreamLogin` (`admin`/`admin`, a public constant of every Cirrus Labs image, never a secret of the owner's). There it makes a private folder (`mktemp -d`, mode 700, owned by the login), puts this Mac's own station binary and `apps/engine/catalog/images/macos-firstlogin.sh` in it, and runs the script as root from that file, its values (the VM user, the image key's public line, the login, the binary's SHA-256) on stdin, never in a command line. The script reads them, then closes its stdin. It installs the binary only when its hash is the engine's, and removes the folder whatever happens. The engine then dials by the image key again.
2. **The key is reachable last, and a marker says the lockdown finished.** The script is idempotent, and its order is the guarantee. It removes its marker (`/var/db/station/locked`) first. It makes the VM user, an admin, or keeps an existing one, and gives it either way a new password made there, a passwordless sudo and an empty `~/.ssh/authorized_keys`. It removes the auto-login and `/etc/kcpassword`; gives `admin` a password made there (`dscl . -passwd` by the old one, which macOS requires of root for an account holding a secure token), unless `admin`/`admin` already fails; empties `admin`'s and root's authorized keys; and removes `admin`'s passwordless sudo (`/etc/sudoers.d/admin-nopasswd`). It writes `/etc/ssh/sshd_config.d/000-station.conf` (no password or keyboard-interactive login, no root login, `AuthorizedKeysFile .ssh/authorized_keys`). It then checks all of it: `admin`/`admin` refused, no `kcpassword`, no `admin` sudo rule, `sshd -T` reading each line, the VM user's sudo. Only then does it write the image key, as the VM user's only authorized key, and its marker, its last step. A failure at any point before the key leaves a guest the key does not open. Up to `admin`'s password, the next connection runs the first login again; past it, nothing logs in, and the create fails for good: the VM is deleted and made again.
3. **A key dial is trusted only with the marker.** After every dial by the image key to a VM whose image carries a lockdown, the engine reads the marker (`test -f`). When it is absent (a lockdown cut between its key and its marker), the engine runs the same lockdown again over that session, as the VM user by its sudo, and keeps the connection only once it exits 0. When it cannot, the dial fails, naming the unfinished lockdown, and the create fails with the VM kept failing SSH answers; no session is opened on such a guest.
4. **A start of a VM whose create failed is its retry even while it runs.** `machines.start` answers `is already running` only for a VM whose create did not fail; one that runs with a failed birth is run (a no-op), waited for and set up as ADR-062 §3 says, so the hint a failed create gives is a gesture that can succeed.

## Consequences

- Footprint in the guest: one admin account named as the Mac's VM user, `/etc/sudoers.d/60-station-user`, `~/.ssh/authorized_keys` and `~/.config/station/` under its home, `/usr/local/bin/station`, `/etc/ssh/sshd_config.d/000-station.conf`, `/var/db/station/locked`. `admin` stays, with a password nobody holds, no authorized key, no sudo rule of its own and no auto-login, so the guest has no logged-in desktop after its next reboot. On the Mac: the image key, made at the first macOS VM when no build made it before.
- `admin`'s passwordless sudo is removed rather than kept: nothing of station's runs as `admin` once the lockdown ran, and a rule nobody needs is one an account recovered later would inherit.
- **The open window.** From the clone's boot until its lockdown changes `admin`'s password, the guest takes `admin`/`admin` over ssh, and `admin` has root by its passwordless sudo. Who can reach it then: anything on this Mac, every other VM on its vmnet NAT network (`192.168.64.0/24`), and, for a workspace made `--network bridged`, the whole LAN the Mac is on. The window lasts the boot and the first login, seconds once sshd answers, since the engine dials as soon as it does. Anyone who reaches it in that time holds root, and nothing the lockdown does afterwards can undo an implant made with root; it resets the entry points it knows (both accounts' passwords and authorized keys, root's authorized keys, the sudo rules, sshd's configuration), nothing more. A bridged workspace is not made on the NAT first and bridged after its lockdown: its network is fixed at its run, so that would cost a stop and a second boot of every bridged macOS workspace, and the reach it closes is the LAN's for those seconds; the trade is the owner's to revisit.
- Passwords on a command line: the VM user's goes through `dscl`'s stdin. `admin`'s cannot: `dscl` asks the old password of an account holding a secure token from a terminal only, and fed through a pseudo-terminal it works only with timed pauses (probed on macOS 26.6.2, 2026-11-23). `sysadminctl -addUser` takes a new account's password only as an argument too (`-password -` needs a terminal); that one is replaced at once through `dscl`'s stdin. Each appears for an instant in a root command line inside the guest, readable only by what already runs there, which in that window holds root through `admin` anyway.
- The guest's station is the binary of the Mac's engine when the VM was locked down. A newer engine does not replace it; the Linux images' baked binary is in the same case.
- What is proved over the fake world, where a guest plays its lockdown and the world cuts it (`world lockdown-cut before-key|after-key`): the key dial refused, the first login as the image's account, the lockdown run from its folder, the marker read, the create made; a lockdown cut before its key runs again at the next connection; one cut after its key runs again over the key before the connection is used; one that never finishes fails the create; a first login refused too keeps the VM failing SSH answers; a running VM whose create failed is retried by its start. The script's order is pinned by `catalog/images_test.go`. The script ran on a real macOS 26.6.2 guest (a throwaway clone of the Cirrus Labs base, cut midway and run again); `ssh <vm>` by the device key on a real Mac is one acceptance run after the train, a macOS guest nesting no VM (`kern.hv_support` is 0).
- ADR-084's `admin` "with a known password" holds for the image, no longer for a VM made from it.
