# Machines

All machines are every machine the owner runs: the physical Macs and the VMs on each. One list shows them, any Mac can drive any other, and a VM is made, run and deleted from the Mac it lives on.

## Macs and VMs

A Mac registers itself with `station init --name <name>`; another Mac is added by its Tailscale name with `station machines add <mac> [--user <login>] [--key <file>]`, once its ssh and its station answer, and forgotten with `forget`, which never reaches it. This Mac knows another Mac by the name it added it by, and by that name alone: every answer of that Mac's engine, the state the window draws included, is held under it, whatever name that engine goes by itself, and every value of that state that is the name it goes by reads as the name this Mac added it by; a sentence that engine wrote, such as a hint or the overview's verdict, still says its own name. A VM is cloned from an [image](images.md) on a chosen Mac. A machine's kind is `mac`, `server` or `workspace` ([ADR-017](../decisions/017-servers-and-workspaces.md)); its system, `macOS` or `Linux`, is its own word. A VM learns its kind from the file its Mac wrote at create; a macOS VM is told from a Mac by `kern.hv_vmm_present`. A VM refuses the commands that only Macs do, with a hint to run it on its Mac.

A machine has one name, used for `preferences.json`, the `~/.ssh/config` block and `--on`; a Mac's name is also its tailnet node. A VM is never on the tailnet: it is reached through its Mac. Every VM has the one login `vm_user`; a Mac's login is its own `--user`.

`station machines` is All machines: a first line that counts the machines, the running, the stopped and what needs you; each Mac with its VMs under it, in the columns MACHINE, KIND, STATE, CPU and MEMORY; then Needs you. A Mac that does not answer in 5 seconds keeps its row, `✗ Unreachable`, and is a finding, never a failure; a Mac that runs another station says which and where to update it. Piped, each machine is one record (glyph, name, kind, its Mac, state, CPU, memory); `--json` is `station.machines.list/v1`.

Each Mac says what it is, read by sysctl and never by a subprocess: its model identifier (`hw.model`), the name that model is shown by (from the catalogue's table, `Mac` for one it does not hold), its chip (`machdep.cpu.brand_string`), its memory and cores, and whether it has a lid (a laptop). A Mac that falls silent keeps what it last said it was. `machines --json` carries it as each Mac's `hardware`. Its capacity is its memory, the 4 GB macOS keeps, what each VM reserves and what is left free for a new VM: a VM reserves its memory while it runs, and a server its record wants running keeps its share while it is down, so the free figure never jumps when it falls and comes back; a create asking more than is free is refused. `machines --json` carries it as each Mac's `capacity`, and names as `roomiest` the Mac that answers, awake, with the most free memory and at least the 2 GB a VM takes (This Mac on a tie), where a new VM goes when none is named. The API's `machines.list` carries the same in every update: `Rooms`, each Mac's capacity under its name (none for a Mac that never said its memory), and `Roomiest`. A size fits a Mac when its memory is at most the free figure, the one rule the create's refusal and every room a client draws share, so the largest VM a Mac takes is its free memory. Each room judges the three presets a new VM is offered in one click, `small` 4 GB, `workspace` 8 GB and `gate` 12 GB, by that rule, each `fits` or `no-room` (`Presets`), and says the largest that still fits, or `none` (`RoomFor`): words.json words it `room for one more gate`, `room for one more workspace`, `room for a small machine`, `no room for another machine`. The menu bar's New VM sheet offers the same presets, 8 GB first. The window's New machine sheet is one watch, `machines.new` (`From`, a machine file, `base-ubuntu` when empty; `On`, the Mac it is opened from): what a create from that file makes asked nothing else (its `Name`, given over every Mac as read, its `Size` and `Lifetime`, the `Lifetimes` a workspace may take, `MinMemory` and `PurposeMax`), the Mac it opens on (`Mac`: the one asked for when it takes a VM, else the roomiest, else This Mac), and each Mac with its room, the most memory a create takes there, whether it takes one now (`Ready`) and why not (`Verdict`: `No room on mac-mini. Choose the other one, or delete a stopped one first.`, `mac-mini does not answer`, `mac-mini is asleep`). `Server` offers a server of the built-in image the file is, a server's size, judged per Mac (`fits` or `no-room`, with a laptop's `This Mac may sleep: a server pauses with it.`); a server follows no owner's file, so `Server` is null for one. A file no VM is made from is refused, `machinefile.not-a-template`. A create is refused below 2 GB of memory, before anything is made (`a VM takes at least 2 GB of memory`, code `machines.too-little-memory`, exit 2).

A VM being created is on the list from its create's first frame, `Creating`, its memory reserved at once: its record carries the step its create runs (`building`, its image built when it was missing; `cloning`, `booting`, `address`, `ssh`, named `image`, `disk`, `boot`, `network`, `SSH`), that step's position among the create's steps and how many there are (five when it builds its image, else four), and how far it is, per mille, until the create ends. Every step reads `Creating`, tone new, then its noun and position, `boot 2 of 4` after `Creating` on a list; the API's birth carries the step, its `position` and `steps`, the `sentence` a client shows as it stands (`Creating: boot 2 of 4`), and the build's own step as its `detail` while the image is built, and the words of each step are words.json's. A build that fails or is interrupted takes the record off with it. A create that fails from its first run on keeps the VM and its birth, failed at its step ([ADR-062](../decisions/062-a-failed-create-stays-on-the-record-until-its-start-or-its-delete.md)): `failed`, the step it failed at, its `cause` (`linux-2 did not boot: …`), the last lines its console wrote then (`last_lines`, as a down server keeps them) and the `sentence` `Failed at boot 2 of 4`, a list row's detail. It reads as its disk and engine say, its memory given back, and is deleted or started at once: a start is its create's retry, the VM run (or left running, never answered `is already running`) then set up from its first boot on as the create would have (a Machinefile's boot is left to `station machinefile apply`), and its birth goes once that set-up answers, or stays failed at the step that failed again. A delete takes it off with the record; an interrupted create keeps no failure, and reads stopped. A create runs in the process that asked it, a command or the engine, and dies with it: its record names that process by its pid and its start, as its Mac's kernel tells them. A VM whose birth's process no longer runs (killed, its Mac restarted), or whose step this station does not know, has no create left and reads stopped, `was left half made`, to start or delete, its memory given back. A create that runs reads `Creating` however long a step takes, an image's build or an engine restart included, and is neither deleted nor edited while it runs (`machines.being-created`); a stop written meanwhile stays, as the create writes back only its birth, its version and what it wants. Its Overview answers meanwhile from its Mac's record, never from a guest that does not run yet: its `overview.read` watch stays open through the create, one update for each step it reaches, `Creating` that step's birth as `machines.list` gives it, its Summary empty; once the create ends the watch carries on as its guest's, whose first answer has `Creating` null. A VM its engine holds stopped is answered the same way, from its Mac's record, its guest never asked: its `overview.read`, a call or a watch, is one Summary with nothing read inside, its `Verdict` `api is stopped.`, tone plain, its line `Start it to read its pages.`; the v2 reading is still refused `vm_stopped`. Two creates on one Mac, from any processes, never both take the memory or the name left: each record lands under the records' lock, its name and memory judged again there. Once made, its engine tells `vm_ready` (`linux-4 is ready on mac-mini`) and the VM is `fresh` for 8 s. `machines --json` carries `birth` (`progress`, `step`, and `detail` while its image is built) while it is being made, with `failed`, `cause` and `last_lines` once its create failed, and `fresh`.

A workspace's create asked of a Mac's engine over its socket, as the window asks it, is guided: the engine keeps it as an act, `machines.create:<name>`, and `engine.guides` answers its Guide, the window's one view of a long act. Its rail is the create's own steps: each build step when it builds its image (`Base system`, `Packages`...), then `Disk`, `Boot`, `Network`, `SSH`; the steps before the one it runs are `done`, that one `now`, the rest `next`, and each step's line, the one the command prints, is the Guide's live line, never a measure. A create that fails is `failed` at its step, the Guide saying what was kept and its repair as a call with its input, never a command: a VM kept stopped offers its start (`Try again` when its birth failed), its delete the quiet gesture, its name typed to confirm; a VM kept running, or a disk with no VM, offers its delete; a create that failed before its first run kept nothing and offers none. A create cut while it runs, by a Ctrl-C or its engine stopped, is `interrupted` at its step. A create that ends `done` reads every step done, and an ended act is kept 10 minutes in `{state}/station/acts.json`. A server's create, and a create a command runs itself (`station machines create`), are not guided.

A running VM whose guest does not answer is never a plain `Running`: its row wears `◐` and says `SSH answers failing`, then the error its Mac's engine met dialing the guest (`Has an address failing` while it has no address), and its Mac's Overview says the same in its VMs line. `VM.GuestError` carries that error in `machines.list`, empty while the guest connects. A dial refused with `no route to host` is said as that error alone; it is the Mac's Local Network block, with its fix, only when the engine's own read of the approval, taken at that dial, says not approved ([ADR-056](../decisions/056-station-names-the-local-network-approval-a-mac-withholds.md)).

A Mac that falls silent is shown as it last answered: for 30 s since its last answer it is fresh, then `stale`, as is a Mac never heard from. A Mac is `asleep` when it falls silent after an answer that said it was going to sleep: a laptop on battery with its lid closed, or any Mac whose engine had heard macOS's will-sleep (`kIOMessageSystemWillSleep`, through `awake/contract.Power`); it is told apart from one that is `unreachable` for a reason Machines cannot tell. An asleep Mac reads `Asleep · last answer 10:00`, and is no `does not answer` finding unless it hosts a server, which pauses with it. `machines --json` carries each Mac's `reach` (`answers`, `asleep`, `unreachable`) and `stale`. Each Mac's engine holds every other Mac's engine state open, so it reads them as they change, never by asking each in turn ([ADR-072](../decisions/072-before-1-0-every-station-runs-the-same-release.md)); a Mac that stops sending keeps its last values there, marked stale, and is dialed again after 5 s, 10 s and 30 s, then every minute ([`engine.state`](api.md)).

```text
5 machines · 4 running · 1 stopped · nothing needs you
 MACHINE KIND STATE CPU MEMORY
 ● This Mac Mac Engine running
 ├─ ○ api Workspace Stopped · persistent 4 CPU 8 GB
 └─ ● linux-1 Workspace Running · ephemeral 4 CPU 8 GB
 ● mac-mini Mac Engine running
 └─ ● infra Server Running · always on 8 CPU 24 GB
```

`station machines <machine>` is that machine's Overview, the one `station overview --on <machine>` prints.

A Mac's Overview opens on its own head, `Summary.Head.Verdict`, apart from what needs you (`Summary.Verdict`): `Online, with N machines running.`, its line how long the Mac is up (`Up 3 days.`), none where that is not known, or, its engine stopped, `The engine is stopped.`. A Mac that does not answer is told by its `Unseen` verdict in `machines.list`, never down. A VM's Overview carries none.

Each Mac of `machines.list` carries its `Standing`, one word of a closed list, the first rule that matches ([ADR-054](../decisions/054-a-machines-standing-is-one-rule-at-each-level.md)): `asleep` and `not-seen` while it does not answer, as its `reach` says; `engine-stopped`; `engine-not-installed`; `online` otherwise, an engine this Mac cannot know included. Its word and tone are `MachinesMacStanding` in `packages/api/words.json` (`online` ok, `asleep` plain, `not-seen` and `engine-not-installed` warn, `engine-stopped` bad). Its `Machines` is the roll-up of that Mac and its VMs, and the list's own `Standing` the roll-up of every Mac: a `State` and the `N` it names, the first rule that matches, read from the standings alone, bad before warn: `down`, a VM down (`N` VMs); `not-created`, a VM whose create failed (`N` VMs); `engine-stopped`, a Mac whose engine is stopped (`N` Macs); `not-seen`, a Mac not seen (`N` Macs); `engine-not-installed`, a Mac whose engine is not installed (`N` Macs); `empty`, no VM at all; `fine`. Each state that counts takes the tone of the standing it counts. A VM of a Mac that does not answer counts through its Mac, and an asleep Mac is no fault. words.json's `MachinesRollUpState` words each after its `N`: `1 machine down`, `2 machines down`, `1 machine not created`, `1 Mac with its engine stopped`, `1 Mac not seen`, `1 Mac without its engine`, `no machine yet`, `all running`.

Each finding of All machines takes its severity from its machine's standing, so a finding never says broken where the standing does not: broken where that standing's tone is bad, a Mac's engine stopped or a VM down (a workspace ended unexpectedly included; a server stopped while its record wants it running is `infra is down`; a VM whose create failed is `linux-2 was not created: it failed at boot`, its fix its start, a call worded `Try again` by the need's `Verb`, never `Start`; a server a reboot loop broke is `infra is broken: rebooting in a loop`, its fix the restart where a workspace's is its delete), else needs a look (a Mac that does not answer, an engine not installed, a running VM whose SSH fails, a server in a loop while a restart walks).

`machines.list` tells each Mac in one sentence, its `Sentence`, the line under its name in the window's header. A Mac that answers says its engine, `Engine running.`, `Engine stopped.` or `Engine not installed.`, then, while its engine runs, how it sleeps, its `Awake`: `Awake until 18:00.`, with `, lid closed` when the keep-awake holds it lid closed, `Never sleeps.` (`Never sleeps, let go while the battery is low.` while the battery guard lets the policy go), `Awake stopped, lid closed on battery.` for 10 min after a guard ended a keep-awake, else `Sleeps normally.`. A Mac that does not answer says since when: `Not seen for 12 min. Asleep or off the network.`, `Asleep, not seen for 2 h.` when it was last on battery with its lid closed, or `Never seen. Asleep or off the network.`.

A server has four sections: Overview, Activity, Ports and SSH (SPEC §3.2). Its Overview adds `Own Tailscale device` when its tooling put one on the tailnet (Machines never installs nor blocks it) and its ssh, for debugging; its SSH section is the one door, the path that reaches it and what Machines leaves to the owner's tooling. Apps, Settings, Disk, Accounts, Background and Awake are refused on it, exit 2: `infra is a server: station does not manage its apps`, `Hint: run station overview for what infra has`. `apps update --all-machines` and `accounts --all-machines` skip a server by its kind and say so.

## Lifetimes

A workspace is ephemeral unless it is made `--persistent` ([Glossary](../concepts/glossary.md)); a server is always on (its record's lifetime is `always-on`, the one mark of its kind). No workspace restarts by itself (SP-4), and a stop never destroys a VM (SP-5). A server whose wanted state is Running starts with its Mac's engine; a stop sets its wanted state to Stopped, so it stays stopped across its Mac's reboots until `start` sets it back to Running. A Mac's servers are listed before its workspaces:

| Event                          | Ephemeral workspace                                   | Persistent workspace                            | Server                                                         |
| ------------------------------ | ----------------------------------------------------- | ----------------------------------------------- | -------------------------------------------------------------- |
| `poweroff` inside the VM       | deleted: disk, reserved ports, ssh blocks, record     | stays stopped until `start`                     | stays stopped, wanted Stopped, `powered off from inside`, told |
| `reboot` inside the VM         | comes back; never deleted                             | comes back                                      | comes back at once, counted, no wait, not told                 |
| Mac reboot or power cut        | stopped, `ended with its Mac`                         | stopped, `ended with its Mac`                   | starts with its Mac's engine, once its disk is unlocked        |
| a crash, or an end not read    | kept, `ended unexpectedly · start or delete it`       | kept, `ended unexpectedly · start or delete it` | boots again after its wait, counted, told                      |
| `station machines stop <vm>`   | stopped, kept with its disk until `start` or `delete` | stopped, kept with its disk until `start`       | stopped, wanted Stopped until `start`                          |
| `station machines delete <vm>` | deleted                                               | deleted                                         | deleted                                                        |

The VM tells its Mac when it powers off: a unit in the image writes `station-intent=poweroff` to its console, and [the engine](#the-engine) reads it when the VM's run ends. The Mac cannot otherwise tell a reboot from a poweroff, so any end it cannot read as a poweroff never deletes an ephemeral workspace.

### Keeping a server

The engine keeps a server running and healthy. A run that crashes, or ends in a way it cannot read, boots again after a wait that doubles from 5 s: 5 s, 10 s, 20 s, 40 s, then 60 s each time. A run that stays up 10 min brings the next wait back to 5 s; the count of restarts goes on (`Restarts ↺ 3 · last just now`). Five restarts within 10 min are a loop: the server reads `✗ In a loop · ↺ 5 in 10 min · waiting 60 s`, the owner is told once, and the engine keeps trying every 60 s. The loop is a finding under Needs you whose fix is the server's restart, its name typed: the engine keeps its waits and never restarts the server on its own word, so a restart is the owner's gesture. A reboot from inside is counted with no wait, and nobody is told. A poweroff from inside is the server's own word: it stays stopped, wanted Stopped, until `station machines start`.

Its check (`--check`, a URL that answers 2xx or 3xx, or a `host:port` that accepts a connection) is run from its Mac. A health check that never passed since the boot is waiting (`◐ Check waiting`), not a failure; one that passed then fails is `◐ check failing since 10:01`, a finding under Needs you. A failing check never restarts the server: what runs inside is its tooling's. When it passes again the finding goes and the owner is told `infra is back · all 4 health steps pass`. A restart, a loop, a poweroff from inside and a return are each told once, to the Mac's notifications and to every watch of the engine.

Each VM of `machines.list`, of this Mac or another, says what the Machines page shows of it, and no other answer carries these:

- `Standing` is the VM in one word of a closed list, the first rule that matches ([ADR-054](../decisions/054-a-machines-standing-is-one-rule-at-each-level.md)): `not-seen` while its Mac does not answer; `restarting` while a restart walks; `creating`; `not-created`, its create failed and its birth kept; `down`, a VM in a loop or ended unexpectedly, or a server in a loop, powered off from inside, stopped while its record wants it running, or running with its check failing; `stopped`; `suspended`; `healthy`, a server running that passes every step; `running` otherwise. Its word and tone are `MachinesVMStanding` in `packages/api/words.json` (`down` and `not-created` bad, `healthy` and `running` ok, `restarting` and `creating` new, the rest plain). Head, Health's `Down.` and the menu bar's down all read it.
- `Head` is the VM in one verdict, the one its page opens on, said by its Mac in its standing's tone: `<name> is down.` with why (`Its check fails since 14:02.`), `<name> is stopped.` (`It holds no memory. Start it to use it again.`), `Restarting.`, `Creating.`, `<name> was not created: it failed at boot.` (its line the create's cause), `Suspended.` or `Not seen.`, else `Running` (a server whose `Health` says `Healthy.`: `Healthy`) and how it stands with its file, its line what it is for and how long it is up (`Fix the flaky test. Up 2 h.`): `, with N differences from its file.` (warn), `, and it matches its file.`, or `, but its file did not read.` (warn, its line why). A workspace bound to no file, and a server, which station sets up nothing inside, are only `Running.` or `Healthy.`. A workspace is bound to no file only when no Machinefile is named after it and none is bound to it; a file it names that is gone, or an extends no source holds, is a file that did not read. `Drift` is the reading the head says, kept by its Mac's engine (`At`, `Differences` over every chapter of `machinefile.drift`, `Unbound`, or the `Failed` words): it reads it after each boot, every 10 min, and at its next step, about a second, after a call that changes the VM ended on it (`station machinefile apply`, an upgrade, an app installed, removed, updated or moved, a setting applied or turned off), so the head tells such a change once that reading answers, within 2 min; a change made in the VM any other way shows at the next 10-min reading. While a running workspace has no reading since its boot, or its Mac's engine cannot read it, its guest not connected, its head is `Running.` and `Pending` is true.
- `Hold` is who holds it and whether it is safe to delete, one `State` of five with its `Sentence`, the first rule that matches: `not-seen` while its Mac does not answer; `always-on` for a server (`Always on. Stopping it needs its name typed.`); `held` while it is created, or runs ephemeral, made by a session, `By` the session that holds it, absent for you (`It is held by its lot, by studio-os-fe: work may be in progress.`); `free` for an ephemeral one stopped (`Stopped. Safe to delete.`); `yours` otherwise (`Yours. Deleted when it powers off.` for an ephemeral one, else `Yours. Stays until you delete it.`).
- `Sections` are the sections its kind has, one flag each: a server's Overview, Activity, Ports and SSH; a workspace's all but Awake and SSH, and a VM whose create failed has its Overview alone, since it never booted. Images is the estate's section, never one machine's, so it has no flag.
- `Gestures` are the gestures its header offers, drawn as the list says: a running VM `stop`, a running server also `restart`, a stopped or suspended one `start`, a broken server `stop` or `restart` (a restart takes a broken VM and boots it again); a VM whose create failed `try-again` whatever its state, its create's retry, which is a start worded apart (its delete is the page's, as for every VM); any other VM, one being created, not seen, ended unexpectedly or a broken workspace, offers none, and a Mac has none.
- `UsedBytes` is the memory its process holds on its Mac now, read by the meter from the process the engine runs it in, absent while it does not run or its Mac did not measure it; each share of a Mac's `Capacity.VMs` carries the same, capped at the share's `Bytes`.

A Mac that does not answer carries `Unseen`, a verdict in its standing's tone, plain asleep and warn otherwise, never bad, since nothing proves it down: `mac-mini has not been seen for 12 min.` (minutes under an hour, hours under 48, then days), or `mac-mini has never answered.`, with the line `Nothing proves it is down: it may be asleep, or off your network.`; `mac-mini is asleep.` when its last answer said it would sleep, with the line `It was on battery with its lid closed when last seen, 12 min.` This Mac, and a Mac that answers, carry none.

A server's `Health`, in `machines.list`, is the engine's verdict on its four steps, with the cause as its line (`Down.` with the line its head draws, a failing check included, `SSH does not answer.`), and a server with no check is `Healthy.` as far as SSH; its `LatencyNote` says `The engine kept no check so far.` or `one check` while fewer than two runs are kept. A Mac's engine says `State` (`running`, `stopped` or `not-installed`), absent when this Mac cannot know it (another Mac, no hypervisor).

While a server is healthy its check runs every 60 s, and its engine keeps how long each run took, in its memory alone (the last 60: the latency now, the median and the peak with its time). A restart walks the four health steps, Running, Has an address, SSH answers and Check passes, and the engine shows the step it runs and when it began (`2 of 4`, Has an address) until all four pass. Each server's last 30 days live in `~/.local/state/station/uptime.json`, written by its Mac's engine alone: a day before the record started is `none` (nothing is back-filled), a day an incident still held at its end, or holds now, is `down`, a day whose downtime all recovered is `restart` (so today turns `restart` the moment the server is back), any other `ok`; with the last 20 incidents, from, to and cause, and the availability over those days to two decimals, rounded down. `machines.list` carries the same 30 days as `Strip` on each server's VM: its cells with their marks, incidents and restarts, the availability, one sentence for the 30 days (`Up 99.93 % over 30 days, 2 restarts`, counting the days the record holds) and one for each cell, its date first (`Tue 10 Nov. Down from 14:05 to 14:09, out of memory; restarted 1 time`), each worded by the engine in its Mac's clock. A server goes down on its record when its run ends unexpectedly, it powers off from inside, or its check fails since it passed; it is back once all four steps pass. Why it went down is read from the last 40 lines of each of its run's two outputs, its serial console then `tart run`'s own, blank and timestamp-only lines skipped: an `Out of memory: Killed process` line is `out of memory`, a `Kernel panic` line `kernel panic`; with none, a poweroff from inside is `powered off from inside`, a crash `the hypervisor stopped it`, a failed check `its check failed`, any other end `it stopped`. Its record keeps that cause and three of those lines, the cause's among them, until it is back. `station machines log <vm>` prints every line its last run wrote, the console's then the hypervisor's own, as words (a guest terminal's colour escapes are left out), read on its own Mac (`--on`); a boot starts both files afresh. Each console line leaves with every secret in it withheld, in that log, in the lines the record keeps and so in the Last lines card and its notice, by [`core/secret`](../concepts/architecture.md)'s `Screen`; the log files on the Mac's disk stay raw. `machines --json` carries each server's `uptime`, `latency`, while it restarts `restart`, and while it is down `cause` and `last_lines`. Requests per minute are not observable by station: the card shows the latency alone (owner decision D-v4, D1).

## The commands

```sh
station machines create api --persistent --memory 12G --disk 80G
station machines create web --from studio-linux # the image built from it, sized as its vm says
station machines create infra --server --check https://infra:6443/readyz --on mac-mini # always on; nothing set up inside
station machines start api # a stopped workspace, its disk as it was left
station machines stop api # asks yes or no; kept with its disk
station machines stop infra --on mac-mini # a server: asks its name typed (--confirm=infra), --yes answers nothing
station machines edit api --memory 16G # applies when api next starts; a disk only grows
station machines edit infra --check infra:6443 # a server's health check, read by its next health run; --no-check removes it

station machines ssh api # prints the ssh command: ssh admin@api
station machines restart mac-mini # a Mac: asks naming the VMs that pause, a planned restart that unlocks itself, waits for its station, starts those VMs again; a VM: power off, run
station machines restart infra --on mac-mini # a server: asks its name typed (--confirm=infra), --yes answers nothing; a workspace asks nothing
station machines delete api # destroys the VM and its grants; asks its name typed (--confirm=api), saying who holds it when one does; an ephemeral workspace nobody holds asks nothing
station machines api # its Overview, as station overview --on api
station machines unlock mac-mini # after a power cut, on its last LAN address: you type its password into macOS's pre-boot prompt
station machines wake macbook-air --tell # a Wake-on-LAN packet from this Mac; told once it answers again
station machines remind macbook-air # nothing sent: told once it answers again
```

`wake` is the way back from asleep (SPEC B5.14). Every answer of a Mac says the hardware address of the interface it answers on your LAN with, and this Mac keeps it on that Mac's record; `wake` broadcasts the Wake-on-LAN magic packet to it (UDP port 9, through `machines/contract.Waker` and its `udp` adapter), and says `wake sent · it answers in a minute or so`. A packet sent says nothing of whether the Mac woke: its answer does. With `--tell` the record keeps the ask, and the engine asks that Mac every 30 s while the ask stands; the moment it answers, `mac_back` (`macbook-air is back`) is told once, to the menu bar and the owner's notifications, and the ask is cleared. `remind` keeps the same ask without sending a packet (`you are told once it answers`), so it needs no hardware address; a Mac that answers already reads `already awake: it answers`, and nothing is armed.

`create` makes an ephemeral workspace unless `--persistent` is given, and asks which Mac when two or more are reachable on a terminal (under `--json` it is refused, naming `--on`). Defaults are image `base-ubuntu` and the size its Machinefile, `catalog/machines/base-ubuntu.machine.yaml`, says, the only file that sets it (4 CPUs, 8 GB, 20 GB, ephemeral), each size with its unit. A size above what the Mac can give is refused before any effect, a missing image's build included, in that Mac's name (`not enough memory on macbook-pro: 60 GB asked, 4 GB left for VMs`, code `machines.not-enough-memory`): macOS keeps 4 GB, and the running VMs hold theirs. It reserves the [ports of the packages](ports.md#what-a-package-sets) its Machinefile installs before the VM first runs; a step that fails before that rolls everything back. It then prints the health steps as they pass (Running, Has an address, SSH answers), its ports, and `linux-2 Created` with its size. A server (`--server`) is named, always on and behind its Mac (`--persistent` and `--network bridged` are refused), sized 4 CPU · 8 GB · 50 GB unless asked; Machines reserves no profile port and runs no first boot inside it: after SSH answers, its check is `◐ Check waiting` (what answers it comes with your tooling), then `infra is a server`, `Station sets up nothing inside`. Made on a Mac that reports a battery, it adds `◐ This Mac is a laptop: box stops whenever it sleeps · see Mac readiness`. From the first run on the VM is kept whatever fails: `linux-2 did not boot: …`, or `linux-2 is kept, failing Has an address: none after 60 s`, each with start or delete as the fix. A running workspace whose guest connection fails is a finding, `fails SSH answers`. A Mac that does not answer keeps its row in `station machines`, `Unreachable · last answer 03:12`, and the VMs it held at that answer as `? Not seen` (the state `unknown`, worded `Not seen`: nothing proves it down); `station machines <vm>` of such a VM reads `infra is on mac-mini, which does not answer`, exit 0. `--network` is `nat` (the default: the VM stays behind its Mac, with no address on your LAN) or `bridged`, lower case only; `bridged` is for macOS VMs only (an iPhone on the Wi-Fi reaching the VM), and a Linux VM shares its [ports](ports.md) instead. With Tailscale HTTPS off, the profiles' variables hold the local URL and `create` adds a `◐ ports` row naming the admin step. `delete` asks the name typed (`--confirm=<name>` in a script, never `--yes`), and takes with the VM the ports declared public for it.

A VM carries what it is for and who made it, both set at its create and kept by its record: `--for "<purpose>"` is free text on one line, at most 120 characters, none when it is not given, and any other is refused before anything is made (`machines.bad-purpose`, exit 2); its creator is the session `STATION_SESSION` names in the create's environment, else `you`, which a create from the window always reads. A session's name follows a VM's (lowercase letters, digits and `-`, 1 to 40 characters) and is never `you`: any other is refused before anything is made, exit 2, `Error: STATION_SESSION "you" is not a session's name`, so no session reads as the owner. `machines --json` carries each VM's `purpose` and `creator`.

`create --from <machinefile>` makes a workspace from a [Machinefile](machinefiles.md), named by its name or by its file: a file of this Mac (`--from qa.machine.yaml`) is first copied among yours, `~/.config/station/machinefiles/`, under the name it says, and the workspace is made from that name; a Machinefile of yours of that name with other bytes is never replaced, and the create is refused as `apply` refuses it. Its image is the one built from it (`studio-linux`, asked to build first like any image not built), and its `vm` gives the lifetime, the resources and the network wherever a flag says nothing, and the folders of this Mac it mounts (`vm.mounts`): every start of the VM reads them from the Machinefile as it says them then, never from the create, and shares each one live through tart (`--dir=<folder>:ro,tag=station-<n>`), no copy made, read-only where the Machinefile says so. A folder that is not on this Mac refuses the start before the VM boots, naming it (`/Users/me/data, which web's Machinefile studio-linux shares at /data, is no folder of this Mac: make it, or take it out of vm.mounts`), where tart alone would end at once with `A directory sharing device configuration is invalid`; an always-on server starts without it instead, since nothing keeps a server down. A start never needs its Machinefile: one that cannot be read (gone, or no longer parsing) shares the folders the last start shared, those still on this Mac, which the VM's record keeps. Either way the start says why in one line, the VM's `detail` (`web's Machinefile studio-linux could not be read (...): it shares the folders of its last start`), and in `daemon.log`. The VM's record keeps the Machinefile's name, which gives its port [rights](ports.md#rights-and-audiences) when no Machinefile is named after the VM. `--from` names the image, so `--image` beside it is refused, and so is a server's Machinefile or `--server` (Machines sets nothing up in a server), a computer's that says `vm`, at its file, and a name one of the Machinefile's chain bears (`base-ubuntu names a Machinefile of web-dev's chain`), since a workspace's own changes are the overlay named after it ([The overlay](machinefiles.md#the-overlay)). Once SSH answers, the first start mounts each folder at its guest folder (`~/` the VM user's home) by a line of the guest's `/etc/fstab` that names its tag, `nofail`; at every later start the engine brings those lines to the Machinefile's before anyone reaches the guest, so a mount taken out of `vm.mounts` leaves `/etc/fstab` and is unmounted, and one added is mounted. The first start then runs the Machinefile's boot phase ([Phases](machinefiles.md#phases)), its `run.boot` lines last: the Machinefile's chain and lock as this Mac reads them now replace the image's copies in the VM user's `~/.config/station/machinefiles/`, `station machinefile apply --phase boot` runs there as that user (a secret stays its `vault:` reference, resolved by the guest), each program of `accounts.grants` is granted this Mac's one password for it, as `grants.add` does (Touch ID asked for each), each program of `accounts.signins` the workspace is not signed in to is left to you with its command, and the image's drift from the Machinefile is read: each package it bakes now that the image holds no lock line of, and each whose lock now asks another method or version. Its page adds `● Boot phase studio-linux`, a row per grant (`● npm granted`, `◐ wrangler not granted: no password for wrangler in this Mac's vault`; two passwords for one program are not granted either, `grant one from the window`; a grant `grants.add` refuses reads in its refusal's words, `◐ npm not granted: this Mac did not confirm you are there: nothing was granted`), a row per sign-in left (`◐ gh not signed in: station accounts login gh --on web`) and `◐ Drift jq is not baked into the image` with `station images build studio-linux` as the hint; what fails there never fails the create. With `--json`, `boot.grants` lists each program, a refused one by its refusal's code and subject (`{"program":"npm","code":"grant.presence-refused","subject":"pw-2"}`), and `boot.signins` each sign-in left with its `command`. With the engine stopped, start, stop, restart, edit and delete are refused (`Hint: station engine start`).

`create` and `start` need tart: without it they are refused before anything is made, `Error: tart is required by machines`, `Hint: station apps install tart`, and a terminal offers to install it then goes on ([Commands](commands.md#rules)).

`create`, `start`, `stop`, `restart`, `edit` and `delete` need the [engine](#the-engine). On a Mac with tart whose engine was never installed, the first of them installs the engine's job and starts it, then goes on. An engine the owner stopped stays stopped: they refuse before any change and the VM is kept (`Error: the engine is stopped on macbook-pro`, `Hint: station engine start`).

In the menu bar, Clean up (one Mac's, or every Mac's) is a sheet of the stopped ephemeral workspaces, each deleted with its disk, its ports and the accounts lent to it; every one checked; a line names the ephemeral workspaces that stay because they run (`linux-1 is still running, so it stays.`). Its button says what it does with what is checked, `Delete 1 ephemeral workspace`, in red. It sends `machines cleanup` with the ephemeral workspaces left checked on each Mac that has one; a Mac left with nothing checked is not asked.

## On another machine

`--on <machine>` runs the command's call there and renders its answer here: `station overview --on mac-mini`, `station apps install gh --on api`. Another Mac is reached through its engine: one `ssh -o BatchMode=yes -- <mac> station engine attach`, which speaks `station.api/v2` frames over ssh's stdio; a VM of this Mac through this Mac's engine, which runs `station guest serve --stdio` over its one connection to the VM. A VM of another Mac rides that Mac's engine: its name is looked up in this Mac's own records first, then asked of every other Mac at once (`machines.list`, 4 at a time, 5 s each); Machines never runs `ssh <vm>`. A name no Mac holds is `Error: no machine named "<name>"`, `Hint: station machines`, exit 2, with nothing dialed under that name; while a Mac is silent the VM may be its own, so the answer is that Mac's `does not answer`. The far side returns data, so the output is this binary's, in tty, pipe and JSON alike. Each connection opens with `Hello`, the far binary's version, the calls it serves and the [abilities](api.md#the-frames) of their inputs it reads: a call it lacks is `Error: <mac> runs station <version>, which has no <call>`, `Hint: update station on <mac> (run curl -fsSL https://spwn.sh/install.sh | bash there)`, exit 1, and a far station on another [release](api.md#the-frames), whatever the call, is `Error: <mac> runs station <version>: this station speaks only to its own release`: with the same hint when the far release is older, or of the numbering before v0.1.0 (a v3 station), and with `Hint: update station here (curl -fsSL https://spwn.sh/install.sh | bash)`, exit 2, when it is newer or this station is a build of no release. A VM's station is the one its image was built with, so for a VM both refusals name that image instead: `Hint: station images build <image>, then make <vm> again from it: station machines delete <vm> --confirm=<vm>, then station machines create <vm> --image <image>`; a far station refuses a caller on another release in turn, `Error: station <version> is not the release the far station runs, the only one it speaks to`, `Hint: update station here (curl -fsSL https://spwn.sh/install.sh | bash)`. A Mac whose station takes the connection and does not answer its `Hello` within 5 s does not answer, and ssh's keepalives (`ServerAliveInterval=2`, `ServerAliveCountMax=2`) end a link that stops passing data. A connection to a Mac serves every call while it answers, and nothing outlives it: a Mac asleep at one call, or whose link dropped, is dialed again at the next, and a call the open connection's `Hello` lacks is asked again of a fresh one, so a Mac upgraded meanwhile serves it. A far refusal is worded by this binary's table; a code this binary does not know keeps the far side's own words. A machine that does not answer is a finding for a read, `✗ <machine> does not answer`, exit 0, and for an action `Error: <machine> does not answer`, `Hint: station machines <machine>`, exit 1; a VM of such a Mac is `<vm> is on <mac>, which does not answer`, worded the same way. It is refused on `shell`, `completion`, `help`, `man` and the hidden plumbing (`engine`, `guest`, `machines pipe`). Bare `station --on api` prints that machine's overview here. After a remote create, delete, add or forget, the local ssh blocks refresh.

### This terminal's machine

`station use linux-1` says `On linux-1 in this terminal. Other terminals stay on This Mac.` and every later command of this terminal runs on linux-1, as with `--on linux-1`; `--on` still wins for its one command. `station use -` goes back to the machine used before (`Back on This Mac (was linux-1).`), `station use this-mac` back to This Mac, and bare `station use` prints the machine and since when. The choice is this terminal's alone: the shell block exports `STATION_TERMINAL`, an id made at each shell start, and the choice lives in `~/.local/state/station/use/<id>`; a choice no command used for 7 days is forgotten. A terminal without the block is refused, exit 2 (`Hint: use --on linux-1, or run station init`). A used machine that is gone is said once by the next command (`linux-1 is gone (deleted at 14:10) · back on This Mac`, the time when this Mac's station deleted it), which runs on This Mac and clears the choice. `shell`, `completion`, `help` and the plumbing run here whatever the choice.

The All machines list asks each other Mac's engine for its own view (`machines.list`), 4 at a time, 5 s each; a Mac that does not answer is a row of its own, never the others' delay. A Mac on another release answers its version alone: its row says it, `Online · runs <version>`, under Needs you with the side to update (`update station there` or `update station here`; two builds of no release that differ, neither known the older, `run the same build on both Macs`), and its VMs are the ones remembered, their state unknown. On a terminal the rows fill as each Mac answers; piped and in JSON the list prints once, whole.

## Tailscale

Each Mac runs the Tailscale app; the owner logs in through the app. Machines only reads it: the first line of `station ports` shows the node, its MagicDNS name, the CLI it ran and what `tailscale serve` exposes, and Machines drives nothing but `tailscale serve` for [shared ports](ports.md#serve-and-https) and `tailscale cert`, which [warms the certificate](ports.md#serve-and-https). A VM has no node, no key and no tag; the owner's Tailscale policy needs no line for Machines.

The app comes in two variants, and Machines takes either:

| Variant      | Bundle id                 | How it got there                                                                                                                     | Its CLI                                                            |
| ------------ | ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `standalone` | `io.tailscale.ipn.macsys` | the cask `tailscale-app`, `station apps install tailscale`                                                                           | `/usr/local/bin/tailscale`, which the cask's pkg installs          |
| `app-store`  | `io.tailscale.ipn.macos`  | the App Store (`Contents/_MASReceipt`); `station apps` lists it `ok`, unmanaged, `app-store`, never upgraded nor removed by Machines | `/Applications/Tailscale.app/Contents/MacOS/Tailscale`, on no PATH |

Every `tailscale` call, the engine's included, runs the CLI resolved at that call by absolute path: `/usr/local/bin/tailscale`, then the App Store bundle's executable, then `tailscale` on PATH (launchd's PATH holds neither `/opt/homebrew/bin` nor `~/.local/bin`); none is the tailnet `absent`. Every call sets `SHLVL`: the App Store bundle's executable answers as a CLI only when `TERM`, `SHLVL` or `TERM_PROGRAM` is set, and launchd sets none of them. A `Warning: client version ...` line, a CLI older or newer than its engine, is dropped before the answer is read. `station ports --json`'s `tailscale` block says the `variant` and the `cli` path used.

With the App Store app, the setting `tailscale-cli`, which `apps install tailscale` applies once the app is installed (`station settings apply tailscale-cli` when the app came another way), makes `tailscale` answer in a terminal, an IDE and `studio doctor` by writing `~/.local/bin/tailscale`, two lines, `#!/bin/sh` and `exec /Applications/Tailscale.app/Contents/MacOS/Tailscale "$@"`: a symlink to that executable crashes (`bundleIdentifier is unknown to the registry`), so a symlink found there is replaced, the script's exact bytes are adopted, and a file Machines did not write, or another `tailscale` on PATH, is left alone. Until it is written the setting reads Not applied; `station settings off tailscale-cli` removes only Machines' script. `apps install tailscale` also uninstalls the Homebrew formula `tailscale` (an older CLI the app supersedes) once the app is installed: `● tailscale formula  uninstalled: the app replaces it`; the formula alone stays, `◐ tailscale formula installed, app absent`.

## SSH

Machines writes one managed block per machine in `~/.ssh/config` on every Mac, refreshed by a bare `machines` and after every change, so `ssh api` works on every machine. On a Mac, a block offers this Mac's [device key](../concepts/glossary.md) first, through the key agent [the engine](#the-engine) serves (`IdentityAgent ~/.local/state/station/agent.sock` and `IdentityFile "~/.local/state/station/device-key.pub"`), then the key `machines add --key` named, else `~/.ssh/id_ed25519` when that file exists (a block never names a key the Mac lacks, so ssh never says `no such identity`); `IdentitiesOnly yes` keeps ssh to what the block names, so an agent holding many keys never runs out of attempts. The agent signs with the device key, which never leaves the Secure Enclave. Its first signature in an engine's life asks for you at the Mac (Touch ID or your password), unless the Mac is run alone: on a Mac whose Never sleeps is applied, the key signs with nobody present from the Mac's first unlock on, its screen locked or not, and each engine start makes that key again when the setting changed, the VMs trusting the new one at once ([ADR-085](../decisions/085-a-mac-run-alone-keeps-a-device-key-that-signs-with-nobody-present.md)). The agent relays every other key to the session's own agent: until a machine accepts the device key, the second key is the one it takes. Off a Mac, a block names its one key and `IdentitiesOnly yes`, or no identity when that key is not there. Every block pins its host key in `~/.local/state/station/known_hosts/<name>` (`StrictHostKeyChecking accept-new`). The three shapes:

```text
Host mac-mini # a host: its sshd, reached by its MagicDNS name
 HostName mac-mini
 User agent
 IdentityAgent ~/.local/state/station/agent.sock
 IdentityFile "~/.local/state/station/device-key.pub"
 IdentityFile "~/.ssh/id_ed25519"
 IdentitiesOnly yes

Host linux-1 # a VM of this host: no hop
 ProxyCommand /Users/you/.local/bin/station machines pipe linux-1

Host api # a VM of mac-mini, seen from macbook: one hop
 ProxyCommand ssh mac-mini -- "sh -c 'PATH=\"\$HOME/.local/bin:/usr/local/bin:\$PATH\" exec station \"\$@\"' station machines pipe api"
```

`station machines pipe <vm>` (hidden plumbing) carries ssh's bytes to the VM's current ip behind its own Mac; it never needs the engine. A VM trusts its Mac's device key first, then the Mac's `~/.ssh/id_ed25519.pub` and every line of the Mac's own `~/.ssh/authorized_keys`, each once, through a managed block of its `~/.ssh/authorized_keys` (`# >>> station hosts >>>`), written by the guest while it holds `~/.ssh` itself, the lock the `authorized-key` setting takes too, an `authorized_keys` larger than 1 MiB, or whose block is damaged (read by the parser the `authorized-key` setting reads with), left as it is, so whoever may log into a Mac may reach its VMs until the device book replaces the last two ([ADR-077](../decisions/077-a-workspace-trusts-its-macs-device-key-first.md), a proposal). `station machines ssh <machine>` prints the command, never runs it, so `$(station machines ssh api)` does.

## Files and editors

Nothing of a Mac is shared into a VM but the folders its Machinefile names in `vm.mounts` ([above](#the-commands)), each one the owner wrote: no flag or setting adds one, because a mounted Mac folder is a hole in the isolation. Beside them, the ssh name is the one door, for files and editors alike:

```sh
scp report.zip api: # one file in
rsync -a project/ api:project/ # a folder, again and again
scp api:out.log . # and back
```

An editor on a Mac opens the VM by its Remote SSH to the same name: Zed, VS Code or Cursor on `ssh://api/~/code`. So there is no `cp` verb and no shared exchange folder.

## The engine

One engine per Mac, under one launchd agent, `com.jterrazz.station.engine`, and no other job ([ADR-076](../decisions/076-spwn-on-a-machine-one-active-app-one-background-job-the-engine-updates.md)). The engine serves the ssh key agent on `~/.local/state/station/agent.sock` from its start, before it adopts the VMs, and writes the device key's public half to `~/.local/state/station/device-key.pub` first; on a Mac with no Secure Enclave it serves none, and says why on an `agent:` line of `~/.local/state/station/logs/engine.log`, before the VMs are adopted. The engine is the socket's one owner: a socket file nobody answers on is replaced, and when another process answers on it the engine says who on an `agent:` line, and `machines` lists `macbook-pro's ssh agent socket is held by Spwn Engine (pid 9006), not its engine` under Needs you, its fix the command that frees it (`launchctl bootout gui/$(id -u)/<label>` for a launchd job, `kill <pid>` otherwise). The engine keeps a connection to the holder open meanwhile, and binds the socket the moment the holder lets it go, with no timer. An agent that fails to open for another reason is listed the same way, `macbook-pro's engine serves no ssh agent: <why>`, its fix `station engine start`. So an ssh started while the engine restarts finds no agent and is refused, until the new engine has started: the agent stops and starts with it, and `station engine stop` stops it too. The engine is installed the first time it is needed: by the first VM command on a Mac with tart, or by `station engine start` (`● engine installed, running · v3.1.0`), which also brings it to this station's version after an upgrade (`● engine restarted · v3.0.0 to v3.1.0`), and restarts an engine of this version that serves no ssh agent (`● engine restarted · v3.1.0`), its VMs left running, adding `◐ ssh agent needs you · held by <holder> · <the command that frees it>` while the socket is still held; `station init` installs no engine. On a Mac with Spwn.app the engine is the one the app carries, `Spwn.app/Contents/MacOS/Spwn Engine`, and its job is the bundle's, under the app's own label, `com.jterrazz.spwn.engine` ([ADR-073](../decisions/073-spwn-app-carries-the-engine-on-a-mac-with-a-screen.md)): `station engine start` run from it registers it with SMAppService, so Login Items lists it under Spwn; a restart unregisters and registers it again; the job runs as `launchctl print` reads it, never as SMAppService's status says, and is installed while the app holds it registered; and the bundle's first start boots the bare jobs out (the engine's, and the key agent's own job `com.jterrazz.station.agent` an earlier release wrote), deletes their plists, unregisters and deletes the `~/Applications/Station.app` an earlier release installed (Spwn.app carries the menu bar), shows the bundle's menu bar at every login the first time and never again, so the Off the window's switch sets stays (`~/.local/state/station/menubar-offered` records it), links `~/.local/bin/station` into the bundle and records what the job starts with, the environment and its log, in `~/.local/state/station/jobs.json`, since its definition in the sealed bundle holds neither. A `station engine start` that starts or restarts that engine's job restarts the bundle's menu bar too when launchd runs it, unregistering and registering its login item, so it runs the binary the bundle holds now and not the copy an update moved away; a menu bar that does not run, quit or switched off, stays so, and the start that first shows it does not restart it. When the menu bar does not come back, the start adds `◐ menu bar needs you · <why> · <the fix>`: switch Show in menu bar on in Spwn's Settings when macOS refused its register, three times, or the `launchctl kickstart -k` of its job when its unregister was refused or launchd still held it 20 s after. On a Mac without the app, the job names no app (no `AssociatedBundleIdentifiers`), since a Mac that holds Spwn.app runs the bundle's: Login Items shows it under the signer's name, and Local Network by the binary's file name ([ADR-073](../decisions/073-spwn-app-carries-the-engine-on-a-mac-with-a-screen.md)). Each restart boots the job out and in again (`launchctl bootout`, then `bootstrap`), never `kickstart -k`, so launchd reads its plist again and takes a binary signed by another identity: a job loaded at login keeps the code requirement of the binary it found then, and can refuse a release that replaced a local build (`last exit reason = OS_REASON_CODESIGNING`). Without launchd on the search path the install says so, `Error: the engine needs launchd: launchctl is not found`, with the folder macOS keeps it in. It runs every VM of the Mac detached (an engine restart never stops a VM), reads how each run ended (the rules of [Lifetimes](#lifetimes)), adopts the running VMs again at its start (its socket appears only once that and the serve reconciliation are done), keeps one ssh connection per running VM to its [guest](ports.md), and holds the reserved ports. It samples the activity of This Mac and of each running VM (from its guest; from its Mac's view of its process while the guest does not answer) every 60 s, every 2 s while a surface shows it (the menu bar open shows This Mac, and a machine's page open in it that machine; the menu bar closed shows none; the terminal UI shows the machine of its Activity or Overview, and All machines every machine of this Mac), and keeps it in its memory alone: the last 6 min every 2 s, the last 24 h every minute; a disk under 5 % free or another finding that breaks is told once. `machines create` returns once that guest is connected and has written the VM's keys block and its ports' env file (60 s, else the VM is kept, failing SSH answers). On a Mac that has not approved station for [Local Network](../concepts/glossary.md), the guest cannot connect and the create says so, `Error: linux-2 is kept, failing SSH answers: macbook-pro has not approved station for Local Network`, its hint the fix (`approve station on macbook-pro's screen, or in System Settings > Privacy & Security > Local Network`), which names Spwn instead of station on a Mac whose engine Spwn.app carries, the name its Local Network row reads; `machines` lists `linux-2 is unreachable: macbook-pro has not approved station for Local Network` until then; once approved, linux-2 keeps `was not created: it failed at SSH` until it is started, the hint saying so (`start linux-2 once approved`), since its first boot never ran. The engine reads that approval at its start, macOS asking on the Mac's screen at the first read it refuses. A refusal in the engine's first 90 s is no verdict yet, since macOS refuses the first read of an app it has just seen replaced, approved or not: the engine reads `checking` and reads again every 2 s; a refusal past them reads not approved, read again every 30 s until the Mac approves station. `station engine start` waits 5 s at most for a checking read to settle, then adds the row `◐ local network needs you · <the fix>` when it is not approved, or `◐ local network checking · if macOS asks, <the fix>` while it still checks (exit 0 both), and `machines` lists `macbook-pro has not approved station for Local Network` on the Mac once its read is not approved, until it is. `machines start` and `restart` return once the new run's guest is connected too: a stop ends the guest's session with its run. That connection shares the VM's host key pin with `ssh`, whichever key type was pinned first. Why a guest does not connect is written to `~/.local/state/station/logs/engine.log`, one timestamped line per new reason. Its `tailscale` calls die with it: each leads its own process group, killed whole when the call ends or times out, and a call a killed engine left running is killed at the next engine start, from its record under `~/.local/state/station/children/`. The CLI is its client over `~/.local/state/station/engine.sock` (protocol `station.api/v2`, [The API](api.md)). With it down, `machines` and `ports` still read the files and show one engine row, and `status` the same row in its Machine section: `◐ engine not installed → station engine start` when the engine's job is not installed (its plist absent, or with Spwn.app not registered), `◐ engine stopped → station engine start` when it is but the job does not answer (another Mac's stopped engine is read and started through it, `station engine start --on <mac>`).

`station engine stop [--yes]` is Stop everything on this Mac: every running workspace stops with its disk kept, an ephemeral one too (only `machines delete` destroys), all at once through the engine's `engine.stop-all`; the Awake session ends and the sharing of their ports with it; then the agent is booted out (`launchctl bootout gui/<uid>/com.jterrazz.station.engine`) and the stop is kept with who asked it, so `station engine` reads `stopped · since 13:40 by the menu bar`; with `--remove` the job is then taken away, its plist deleted without Spwn.app and the bundled job unregistered with it, and `station engine` reads `not installed`. A server is skipped and says so, and while one runs the engine keeps running for it: `infra skipped (server) · the engine keeps running for infra`; `station machines stop infra` stops it. A VM that will not stop keeps the engine running (exit 1). Off a terminal, a stop that would stop a VM needs `--yes`. `station engine start` bootstraps the agent again; the VMs it stopped stay stopped, and a login starts the engine again whatever stopped it.

The engine reads Machines' latest [release](../concepts/glossary.md), the newest of `jterrazz/spwn` on GitHub not marked pre-release there that carries this Mac's binary, `station-darwin-<arch>`: a release made before its darwin assets are attached is not taken, and the one before it stays. `engine.refresh-release` asks GitHub now and keeps its answer in `~/.cache/station/release.json`; `engine.read-release` answers what was kept, with no network. Both answer the version the engine runs, the latest release and its notes, whether this Mac is behind it, when GitHub last answered and the last ask it refused since, and a head the window draws as given: `spwn v0.22.0 is out.` over `This Mac runs v0.21.0.`, `This Mac runs the latest release.`, `This Mac runs v0.21.0-alpha.1, past the latest release v0.20.0.`, `The latest release is not known yet.`, or `This Mac runs a build of no release.` for a version that is no release (`dev`, a dry run's `dry-run-<sha>`), never behind. A GitHub that does not answer refuses the ask, `Error: the latest release was not read: GitHub: <cause>` (`engine.release-unreachable`), and the read keeps the last answer beside the refusal. Neither call has a command: the window makes them ([ADR-059](../decisions/059-the-latest-release-is-read-by-two-calls.md)). The engine of a Mac asks on its own at its start, then 6 h after GitHub's last answer and 30 min after a refused ask, both counted from the cache so a restart asks no sooner, and it tells nothing of what it reads.

## Mac readiness

The Overview of a Mac that hosts a server, or that has any of its first three checks in force whoever set it, ends with Mac readiness, six checks in this order, each measured on that Mac: restarts after a power cut (`restart-after-power-cut`), never sleeps (`never-sleeps`, or the Mac's own sleep off, `pmset` sleep 0), logs in by itself (`autologin`), disk unlock after a power cut (FileVault on is `◐ needs you`, its fix `station machines unlock <mac>` from the same network), planned restarts unlock themselves (`fdesetup supportsauthrestart`, a fact), engine starts at login (the engine's job installed, else `station engine start`). A setting that is set says who set it: `set by Machines` when Machines keeps a record of applying it there, `set by hand` when it does not, and never sleeps reads `set in System Settings` when the Mac's own sleep is off and the setting is not applied. One partly there reads `changed since` when Machines applied it, `partly set` when it never did. A setting not set names its fix, `sudo ~/.local/bin/station settings apply <setting>` where it needs root, so the line runs whatever sudo's PATH. A Mac hosts a server when one of its running VMs says it is one, asked of its guest's station. Any other Mac has no readiness, and reads no fact for it but its own sleep.
