# Images

An image is a versioned, read-only VM disk that VMs are cloned from. Each Mac holds its own: built there from a Machinefile, the image named after it, or fetched where a registry offers it ([ADR-044](../decisions/044-an-image-is-baked-from-its-machinefile.md)). Machines knows one base per distro ([ADR-051](../decisions/051-a-machine-is-a-base-and-its-machinefiles.md)): `base-ubuntu`, `base-debian` and `base-macos`, each named after its built-in Machinefile and sized by its `vm.resources`, `base-macos` fetched only, from the Cirrus Labs image its Machinefile pins by digest ([ADR-084](../decisions/084-base-macos-is-fetched-from-cirrus-labs-pinned-by-digest.md)); every Machinefile of yours or of the shared source that says a VM's `vm.image.from` on Ubuntu or Debian is an image too (`studio-linux`). ADR-051's `clt` and `xcode` as Machinefiles are not built yet, and `base-macos` built here waits on a macOS recipe (ADR-084).

| Section           | Answers                                                 |
| ----------------- | ------------------------------------------------------- |
| Listing           | `station images`, every Mac's                           |
| Building          | `station images build`, the Machinefile and the version |
| Updating          | `station images update`, a version a registry offers    |
| The recipe        | The plumbing, the image phase, and the cleanup          |
| The binary inside | `--binary`, the release's asset or `make build-linux`   |
| Cleaning          | `images delete`; Tart's pull cache is `disk free tart`  |

## Listing

```sh
station images                  # ●  base-ubuntu  2026.11.01  4.0 GB  macbook-pro  api · linux-1
station images --on mac-mini    # that Mac's alone
station images --json           # station.images.list/v1: name, version, distro, size_bytes, mac, vms, newest, deletable, orphan, building
```

One row per version per Mac, This Mac first, then every other Mac that answers, named as This Mac added it whatever name its engine goes by; an image no Mac holds is one row, `not built yet`, or `not fetched yet` for a fetch-only one (`base-macos`), with the hint `station images update base-macos`. An image whose Machinefile is gone from every source and the catalogue, but whose record is on the Mac's disk, is listed all the same as an **orphan** (`orphan` in `--json`, the reason `orphan` on its row, which says its Machinefile is gone, then the VMs made from it or none): it is never the newest, so it is deletable once no VM is made from it, by its name like any other (`images delete station-linux@2026.11.17`); a record an older station wrote is its row too, and never stops the list. Images live on a Mac: inside a VM the family is refused (exit 2).

A version is deletable when it is not the newest of its image, no machine was made from it and no build is making it; `Report.Unused` in `apps/engine/images/record.go` is that one rule, and `images.list` says it as `Deletable` (`deletable` in `--json`), the same rule that lists the versions [Disk](disk.md#what-nothing-uses) frees with the leftovers, through this delete.

An image being built is one more row, the version it will be, at its step: `Step 2 of 4` (`building` in `--json`). The four steps are the build's: Base system (the upstream pulled, cloned and booted), Packages (the station binary and the plumbing recipe), Settings (the Machinefile's image phase) and Seal (the cleanup, the power off and the record). A build marks its step in a file of `~/.local/state/station/builds/`, with the process it runs in, and clears it when it ends; `images.list` runs at its target, so the process that answers it reads those marks (on This Mac, the CLI's own), not the engine, and a mark whose process no longer runs is no row. The building row also lists the four steps in order (`Walk` in `images.list`), each with its `State`, `done`, `now` or `next` (a closed list: `ImagesBuildState` in `packages/api/words.json`, `done` ok, `now` new, `next` plain), and the word the engine says it by, so a client draws the walk and never works out which step has passed; a build at Seal reads `done`, `done`, `done`, `now`. The version a build is making is not deletable.

## Building

```sh
station images build                  # every image missing, or whose recipe, Machinefile or lock changed
station images build base-ubuntu    # the built-in Linux workspace
station images build studio-linux     # a Machinefile of yours or of the shared source
```

An image is built from a Machinefile of a VM that says `vm.image.from`, the upstream its disk starts from (`ghcr.io/cirruslabs/ubuntu:24.04`, pulled once, about 5 GB, and cloned for the build), read from every source as `station machinefile plan` reads it: a name no source holds is `no image "<name>"`, and a Machinefile that makes no image (a mixin, a computer's, a VM's with no `vm.image.from`) is refused naming why, both exit 2. The version is the UTC date, `2026.11.07`, with `.2` for a second build the same day. The record keeps the upstream, the Machinefile, the hash of the recipe files and the hash of the Machinefile's chain (every file it extends, its overlay) and lock, so a bare `build` rebuilds an image whose recipe, Machinefile or lock changed; it also keeps the lock the build VM wrote once its image phase ran, the versions the image carries. Images need Tart: `station apps install tart`.

`base-ubuntu`, `base-debian` and `base-macos` are the built-in images' only names: `linux`, `station-linux` and `macos` name no image in `machines create --image` (`unknown image "macos"`), and an image built under an old name is never read to make a machine, only listed and deleted as an orphan ([ADR-051](../decisions/051-a-machine-is-a-base-and-its-machinefiles.md)).

Every record names the image's distro, `ubuntu`, `debian` or `macos` (`catalog.Distro`, worded Ubuntu, Debian and macOS), and its version, the built-in image's Machinefile's `system.version` (`24.04`, `13`, `26.6.2`); the image of a Machinefile of yours is the distro of the recipe it is built with, the one its `system.os` names (Ubuntu when it names none). A record that names no distro, one an older station wrote, is read no more: every images command that reads its image exits 2 with `image.old-record`, naming the file and `station images delete <image>@<version>`, the one gesture it lets through while no machine was made from that version and no build is making it. That delete removes the record and the version's disk; the next create that needs the image builds it again.

`base-macos` has no recipe: a macOS workspace starts from `ghcr.io/cirruslabs/macos-tahoe-base`, pinned by digest in the `base-macos` Machinefile's `vm.image.from`, as Cirrus Labs made it; `images build base-macos` is refused with the hint `station images update base-macos`. That image holds no key of Machines, only its `admin` and the password Cirrus Labs gives every image, `admin`. So the engine's first connection to a new macOS workspace, refused by the image key, logs in once as `admin` by that password and runs its lockdown, `apps/engine/catalog/images/macos-firstlogin.sh`, as root from a private folder it puts it in with this Mac's own station, its values on stdin ([ADR-087](../decisions/087-a-fetched-macos-guest-takes-its-key-at-its-first-login.md)). Once that hash is the engine's, it refuses a VM user the rule of `vm_user` refuses ([Preferences](preferences.md)), or the image's own `admin`, before any change, so a refusal leaves the image as it was and the engine stops the workspace; then it first closes what the image's login opens: it turns sshd's password, keyboard-interactive and root logins off (`/etc/ssh/sshd_config.d/000-station.conf`), removes the auto-login (`/etc/kcpassword`), gives `admin` a password made there and never kept, empties `admin`'s and root's authorized keys, and removes `admin`'s passwordless sudo. Then it installs station as `/usr/local/bin/station` (`root:wheel`, 755, in a `/usr/local/bin` it makes `root:wheel`, 755), makes the VM user (an admin, its password made there and never kept) with a passwordless sudo (`/etc/sudoers.d/60-station-user`, checked by `visudo` before it is renamed to that name), and gives the image's Homebrew (`/opt/homebrew`) to the VM user. It replaces the host keys every clone of the image shares with the guest's own and prints the new one, which the engine pins instead of the old one in the workspace's known hosts. It checks every one of those (`admin`/`admin` refused, `sshd -T`), and only then writes the image key in the VM user's `~/.ssh/authorized_keys` and, last, its marker, `/var/db/station/locked`. The engine then connects by the image key, and keeps a connection to such a workspace only once that marker is there: when it is absent, it runs the lockdown again over the key first. A lockdown that fails, or does not finish in 3 min, stops the workspace at once, so it runs once per start, and its create fails at SSH with the lockdown's own cause. When the guest still takes `admin`'s default password (a lockdown cut before it closed it) or the key (one cut before its marker), its `start` runs the lockdown again; when it takes neither, the cause says so and the hint is `station machines delete <vm>, then make it again`.

## Updating

```sh
station images update           # every image this Mac holds
station images update base-ubuntu     # ●  base-ubuntu  2026.11.03  fetched
station images update base-macos      # ●  base-macos   26.6.2      fetched
```

The registry holds no image yet, so each Mac builds its own. An update still asks the registry `ghcr.io/jterrazz/station-<image>` (one tag per version) for the newest version, and an image it does not offer (the registry answers 403 or 404) exits 1 with `image base-ubuntu is not released` and the hint `station images build base-ubuntu`, the gesture that makes it here. An image Machines has no recipe for and no registry releases, a macOS Machinefile of yours, exits 1 with `no version of <image> is released`, and its hint says that nothing on this Mac can fetch or build it, rather than naming a gesture that would be refused again. A version the registry does offer is fetched only when it is newer than every version held: `is the newest` otherwise. The fetched version lands whole as an image disk beside the others, or not at all: a registry that does not answer, or a fetch that fails, exits 1 and leaves the image as it was. Like a build, it changes only the next VMs.

A fetch-only image of the catalogue, `base-macos`, is updated from its pin rather than from that registry: the upstream its Machinefile's `vm.image.from` names by digest, at the version its `system.version` says (`26.6.2`), through the same fetch, clone and record. The record keeps the digest as its `upstream`, and `station images` lists it with its version and its size (about 50 GB). A version held at or above that one is `is the newest`. A new pin moves the version in the same commit, so a re-pin at the same version is fetched only after `station images delete base-macos` ([ADR-084](../decisions/084-base-macos-is-fetched-from-cirrus-labs-pinned-by-digest.md)).

## The recipe

The recipe is the base plumbing of a system, shell files embedded under `apps/engine/catalog/images/`; what the image carries is its Machinefile's. Ubuntu and Debian run the same files: `base-debian` over `ghcr.io/cirruslabs/debian`, Debian 13 pinned by digest in its Machinefile, `base-ubuntu` over `ghcr.io/cirruslabs/ubuntu:24.04`. The build copies the `station` binary into the build VM, then runs three sessions inside it behind its Mac, each over Machines' own ssh client: the first by the base image's password, the others by the image key the first installs:

1. as the upstream's own user, `linux.sh` creates `vm_user` with passwordless sudo (the rule is `/etc/sudoers.d/60-station-user`, a name with no dot, since sudo skips a file whose name has one and a login may; the build checks it with `visudo -cf` and fails with the cause if `sudo -n` still asks `vm_user` a password) and the Mac's image key, its `~/.config/station/machinefiles` folder, and the `docker` group with `vm_user` in it; installs only what the plumbing itself uses (zsh, the user's shell; `curl` and the certificates; `cloud-guest-utils`, which grows the disk; `libatomic1`, which node's Linux builds link); the `station` binary; lets sshd carry the engine's forwards (`/etc/ssh/sshd_config.d/60-station.conf`: `AllowTcpForwarding local`); runs `station init` for the shell block; installs three systemd units: `station-intent` (tells the Mac about a poweroff, see [Machines](machines.md#lifetimes)), `station-hostkeys` (generates ssh host keys at first boot, ordered before `ssh.socket` outside the default dependencies, which would make a cycle) and `station-growroot` (grows the root partition and its filesystem at every boot, so a disk `machines edit --disk` grew is used); turns off what a VM never uses: cloud-init (`/etc/cloud/cloud-init.disabled`: a clone keeps the network it rendered at the build, every `en*` link by DHCP whatever its MAC), the wait for every link online (`systemd-networkd-wait-online`, masked: the engine waits on sshd, which answers once the address exists), and ModemManager, multipathd, udisks2, fwupd and motd-news, masked; it keeps unattended-upgrades and its apt timers, a VM's only source of security updates (the night upgrades a Mac's Machinefile apps, never a guest's system); masks the getty on `/dev/hvc0`, since tart reads the console file back into the guest as input; and makes `hvc0` the kernel's console (`/etc/default/grub.d/60-station-console.cfg`, checked in the generated `grub.cfg`, the build failing without it), so the kernel's lines reach the console file a server's down cause is read from;
2. as `vm_user`, the image phase: the build puts every file of the Machinefile's chain that is not Machines' built-in one, and this Mac's lock of it (its shared source left out), into `vm_user`'s folder, and `linux-bake.sh` runs `station machinefile apply --machinefile <name> --phase image` there, which installs what `vm.image.bake` lists, each listed package of the image phase, and what they require ([Machinefiles](machinefiles.md#phases)), then prints the lock that run wrote, which the image record keeps. `base-ubuntu` bakes `linux-kernel` (Ubuntu 24.04's hardware-enablement kernel, `linux-image-virtual-hwe-24.04`, the one kernel the image keeps), mise, git, Docker, `build-essential` and `playwright-deps` (the libraries and fonts headless Chromium needs on Ubuntu 24.04), so a fresh workspace runs a browser gate and `docker run`. `base-debian` bakes nothing: a Debian machine carries the plumbing and what its own Machinefile adds;
3. as `vm_user`, `linux-cleanup.sh` stops the upstream's `tart-guest-agent` (it runs as `admin`), removes the upstream's user and fails the build if it cannot, empties the machine id and the host keys, purges what a VM never runs (when the image phase installed a kernel, every other kernel with its headers, utilities and metapackages, and the firmware of physical devices; snapd and its seeds; the eBPF tracers; Mesa's Vulkan drivers), never a package the image phase installed (the build fails with the package's name if apt's plan for the purge would take one, and if grub then boots no kernel it kept), builds the kept kernel's initramfs again (a firmware package rebuilds it when installed, never when purged, so it would still carry the purged firmware), and powers off.

The plumbing is bounded at 30 minutes, and the image phase at 35: 15 for its packages, then 20 for its `run.image` lines ([Phases](machinefiles.md#phases)). A VM's first boot sets its own name and machine id and grows the disk. No tailscale is in the image: a VM is reached through its Mac ([Machines](machines.md#ssh)).

A build is raced by no package operation of its own base. The upstream's daily apt timers are overdue at every boot of a clone, and the unattended upgrade they start holds dpkg's lock for minutes, so before its first `apt-get` the plumbing stops them for the build's boot, waiting for a run they already started rather than killing it, and makes every apt run of the image wait up to 5 min for another's lock (`DPkg::Lock::Timeout` in `/etc/apt/apt.conf.d/60-station-lock-wait`, which the upstream sets for `apt` alone, so `apt-get`, and an install script that runs it, docker's, waited for nothing). The timers stay enabled: a VM made from the image runs its daily security updates.

A build that fails leaves no build VM: it is deleted with its half image. One whose image phase fails says, from its apply's own lines, which packages failed (`image base-ubuntu: the image phase failed: 4 of 12 packages failed: docker, ...`, the first 8 named, the rest counted), and before the VM goes it copies the last 64 KiB of each one's log to This Mac, `~/.local/state/station/logs/station-build-<image>.<package>.log`, each named on its line of the error; a VM that no longer answers is said so in the error, which stays the build's own. A `machinefile apply` that fails in a VM keeps its logs there, `~/.local/state/station/logs/<package>.log`, since that VM stays.

## The binary inside

The image carries `station-linux-arm64`. A release build downloads the asset of its own version into `~/.cache/station/` and checks it against the release's `checksums.txt`. A build whose version is no release's tag (a development build, a build of a branch, signed or not) has none to download: the refusal says this station is not a released version and names where a customer gets it, the `station-linux-arm64` asset of a release at `https://github.com/jterrazz/spwn/releases`, and `--binary` takes that file. From a checkout, `make build-linux` makes it:

```sh
station images build base-ubuntu --binary ~/Downloads/station-linux-arm64
make build-linux && station images build base-ubuntu --binary .artifacts/go/station-linux-arm64
```

## Cleaning

`station images delete <image>@<version>` deletes only a deletable version: the newest, one a machine was made from and one a build is making are refused (exit 2, `image.in-use`), naming why, whichever client asks; a bare `<image>` deletes every version, the newest included, but is refused (`image.in-use`, "being built") while a build of that image is making one. A delete never touches a VM: a VM is an APFS clone, independent of its image once made. Bare `station images` marks every version older than the newest. Deleting never prunes Tart's cache of the upstream: that cache is Tart's, emptied by `station disk free tart` ([Disk](disk.md)), and the next build pulls the upstream again after it. A delete that leaves no image on the Mac says so, in a line under its rows, with the gesture: `The upstream disk tart downloaded stays for the next build: station disk free tart frees it`; the delete frees nothing of that cache, which is shared by every build.
