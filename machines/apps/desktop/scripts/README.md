# The window's bench

Every job the window's makers run, one script each, in the Linux VM only, `look.sh` aside, which only copies to the VM and asks it: a Mac never installs, builds, tests or opens the window. Each runs from any copy of the repository with no argument, and shares one cache, `$STATION_BENCH` (`~/bench` by default). Go's module and build caches are the one exception: each copy keeps its own under `.artifacts/go/`, seeded on its first run from the bench's `gomod/` and `gocache/` (hard-linked, else copied), so two copies building at once never write the same Go cache; its directories are writable (`-modcacherw`), so `rm -rf` removes a copy.

## What a recording holds

A recording is generated: the root's `make generate` runs `record.py` over every world on Linux (one line of skip elsewhere), after the engine's own projections, so a change to the engine regenerates the answers the window replays in its own commit, and the gate's rule that `make generate` leaves the tree clean is what fails a stale one. It runs `record.py --if-moved`, which skips the run, in one line naming its key, when nothing it reads (the world build's Go sources, embedded files and catalog, the Go version, `scripts/*.py`, `specs/usecases/worlds/`, the fixtures `WORLDS` names) and nothing it holds (every byte under `src/fixtures/worlds/`) moved since a run that succeeded; the key is kept in the root's `.artifacts/window-record.stamp`, never committed, and in `$STATION_BENCH/record-keys/<key>`, the store every copy of the repository shares, where a run that recorded every world and left the recordings unchanged (the key after equals the key before) leaves it, so a fresh clone of a tree the bench already recorded skips too. The line it prints names the evidence, `stamp` or `store <path>`; with no `STATION_BENCH`, or a key the store lacks, a cold gate records, and `WINDOW_RECORD_FORCE=1` records all the same. No file under `src/fixtures/worlds/` is edited by hand; a world is a line of `WORLDS` (`world.py`), a read a line of `asks`, `follows` or `ALSO`, a gesture a line of `GESTURES`.

Two runs of `record.py` over the same tree write the same bytes.
The world build has no fixed clock (`apps/engine/wire/world_on.go`), and what a watch streams before it settles comes in the scheduler's order, so the recorder keeps only what no run decides: a watch's first and last answers, the last alone for a watch of `SETTLED` (`disk.read`, whose first answer races its walk) and for an `overview.read` that streams no birth (its summary answers once per part in the order the parts arrive, and its last, before the engine's done, is the whole Overview); a gesture's reads in the world's order of asks, judged changed with the clock's fields left out; no read of `TIMED` after a gesture, but the activity of the VM a gesture of `MEASURED` (`machines.stop`) stopped, which measures nothing.
A gesture of `GESTURES` may name, in `following`, a gesture made before it in the same world (a Start after a Stop of the same VM): its reads are judged changed against what they answer once that one is made, as the window holds them once it has played, and the file holds the gesture without the field. It may also name, in `preferred`, preferences of This Mac set by hand before it (a Try again after `vm_user` turned to one the rule refuses): the door's engine ends, the world it wrote back takes them, and the door opens again over the same HOME, so its acts and records are kept and its reads are judged against what they answer then.
A gesture may also name reads `during` it (a create of linux-2: `machines.list` and linux-2's Overview): they are asked on its door once its first frame is in, while it runs, and kept under `during` as any read is kept, changed or not, so the replay answers them from its first frame to its last ([Making a gesture](../README.md#making-a-gesture)). The world build serves them in one order on every run: the create's first frame, then those reads, each answered between the same two of its frames (`door.py`, `ask`).
The acts the engine guides (`engine.guides`) are the one read asked of a second `station guest serve --stdio` over the door's own HOME (`door.py`, `apart`), as the stories ask it: an engine reads the board a live act left in `acts.json` as it starts, so a read made on the door that runs the create would never see it. While a gesture runs it is asked once its holds are reached; after it, once the door's engine has been stopped and its world written back.
It carries over from the file's last recording `engine.start`'s process number (`NOISE`) and the world's clock fields (`CLOCKED`: `settings.matrix`'s `Read`, `awake.read`'s `Now`): nothing else is rewritten, since the rest is the engine's answer.
Each door opens on a world whose engines took one turn first (`station --version`), as a Mac's engine runs before the window opens, so what an engine keeps beside its loop (a VM's drift, its head's count) is in the answer. That turn is taken once per world (per seed and fixture) and its HOME is copied for every door, each door keeping a private copy.
A watch of `UNENDED` the engine holds open (a VM being created streams its overview, each answer a `Creating`, for as long as the birth lasts) is cancelled by its id after `QUIET` seconds of silence, as the window cancels a watch it lets go of, and its answers are those that came before; any other watch is waited for to its end, since one that settles (`disk.read`) or an Overview whose slowest part is still out may be silent longer, and a request still open after `WHOLE` silences in a row stops the run rather than write a part-read answer.
So a file a run rewrites is a change of the engine's answer or of the recorder's tables, never noise: commit it with the change that moved it.

## Starting a lot

The window is a member of the root's npm workspace, so a copy of the worktree is all the bench needs. From the Mac, copy it without its `.git`, then set up and prove in the VM:

```bash
rsync -a --delete --exclude .git --exclude node_modules --exclude target --exclude .artifacts ./ design:window-<lot>/repo/
ssh design 'cd window-<lot>/repo/apps/desktop && bash scripts/check.sh'
```

`check.sh` and `check-quick.sh` run `bench-setup.sh` first, so a copy synced again needs nothing else.

The scripts take the toolchain the host declares: `NVM_DIR` for node, `CARGO_HOME` for cargo and a Go already on `PATH`. A host that declares none gets `~/.nvm`, `~/.cargo` and `~/go-sdk`.

The first `fix.sh` on a fresh copy reports one root finding: `docs/guides/test.md` names the proof build's folder under `.artifacts`, which exists only after the first build. Run `check.sh` once, then `fix.sh` is clean.

Run `check.sh` once WITHOUT `--update` before your first change: its failures are the ones you start from, and a golden that `--update` rewrites later is then yours to read, never one you inherited unseen. Once you change a page, `--update` rewrites its goldens, and you look at each before you commit it.

A test waits on a region (`within(region('…'), content('…'))`, a heading, a button by its name), never on a text that a row splits across elements: `content()` matches one element's text, so a sentence drawn as a title, a chip and a sentence is never seen whole, and the wait times out.

## The root's findings

The root's count is not the window's to clear: a finding outside `apps/desktop` belongs to the root's gate, `make check`. It is 0 on a fresh copy, as it is on the main it was cut from, every copy resolving `@jterrazz/typescript` 12.3.0 (measured 2026-11-16 in the VM `design`). The window's own findings, its layers among them ([the dependency rule](../README.md#the-dependency-rule)), are counted apart: the root's check reads them too, and `check.sh` prints them as `window findings`.

## How long the Tauri window takes to open

About 30 s from the debug binary's exec to its window mapped, under Xvfb and openbox in the VM `design`, each run with a fresh sandbox HOME and display over `serve-world.py two-macs`; its first connection to the engine follows 0.6 s later. Measured 2026-11-13, three runs each, the binary built with `--features tauri/custom-protocol`:

| Head                                      | Window mapped (s)   | First connection (s) |
| ----------------------------------------- | ------------------- | -------------------- |
| `8e42fdf00`, before the law and core lots | 30.20, 30.21, 30.21 | 30.85, 30.86, 30.86  |
| the merge of both lots                    | 28.55, 30.21, 30.23 | 29.14, 30.84, 30.87  |

The merge is not slower. The wait is the same to a hundredth on every run: HYPOTHESIS 2026-11-13, a timeout of the environment (a D-Bus or portal call) the webview waits out, not work of the window; one run under `strace -f -tt -e trace=connect,poll,ppoll` shows which call it waits on.

## What stays behind

- In `$STATION_BENCH`: `npm-cache/`, `pw/` (Chromium), `gomod/` and `gocache/` (only read, to seed a copy's own), `worlds/` (one world build per state of the Go sources), `noreserve/` (the shim). Kept on purpose: it is what makes the next copy set up in seconds; `rm -rf ~/bench` empties it.
- In `$STATION_BENCH`, also `tauri-target/`: the Tauri build and the bridge's test build every copy shares, a few gigabytes, so a copy's `src-tauri/` keeps no `target/`. Its dependencies are built once for all; the window's crate has units of its own per copy's folder (cargo keys a path package by its path). Cargo dates an input by its mtime, which the sync carries from the Mac, so a folder synced again with a different file dated before its last build was served that build: `tauri_inputs_dated` (`bench-env.sh`) touches the crate's inputs, `bridged.ts` included, when their content moved since the folder's last build, its stamps in `tauri-target/.inputs/`. The window a Tauri session opens is the copy's own, `.artifacts/spwn-window`, taken under a lock as it is built: `debug/spwn-window` is whichever copy built last.
- In the copy: `node_modules/` and the window's artifacts folder (the bench's logs, the proof build, the captures, `go/`, the copy's Go caches). The Tauri scripts remove `src-tauri/gen` and `src-tauri/Cargo.lock` when they end, and no Python run writes `__pycache__`.
- In the temp folder: nothing; every world session (`window-world-*`) and seed (`window-seed-*`) is removed when its process exits, by its end, an exception or SIGTERM (`world.py`, `temporary`); a SIGKILL alone leaves one.
